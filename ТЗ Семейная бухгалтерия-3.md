# ТЗ: Семейная бухгалтерия

Oct 13, 2026 · @Aleksey

## 1. Назначение и термины

Система ведёт личную и семейную бухгалтерию нескольких людей: учёт счетов и транзакций, планирование регулярных платежей и контроль лимитов по дереву категорий. Интерфейс и описания транзакций — на ru, en, th.

Цели первой версии:

1. Несколько пользователей ведут общий и раздельные бюджеты без дублирования справочников.
2. Одна покупка (чек) раскладывается на позиции с разными категориями.
3. Регулярные платежи видны в календаре заранее; транзакция появляется только после подтверждения оплаты.
4. Бюджет на неделю, месяц и год показывает план, факт и лимит по каждой ветке категорий.
5. Расход добавляется с любой страницы за ≤ 5 секунд (раздел 10).
6. Гость видит лендинг и регистрируется через email, GitHub или Facebook (разделы 11–12).
7. Интерфейс готов к продакшену: единая дизайн-система, WCAG 2.1 AA, телефон и компьютер (раздел 9); защита по OWASP ASVS уровня 2 и двухфакторная аутентификация (раздел 13).

| Термин | Значение |
| --- | --- |
| Проект | Бюджет, к которому привязаны люди, счета, категории и транзакции. Личный — один участник, семейный — несколько |
| Участник | Пользователь в проекте с ролью owner, editor или viewer |
| Транзакция | Шапка операции: дата, счёт, тип, описание. Сумма = сумма позиций |
| Позиция | Строка транзакции: сумма, категория, своё описание |
| Лимит | Предел расходов категории за период; действует на всё поддерево |
| Плановая операция | Шаблон расхода или дохода с правилом повторения; порождает вхождения в календаре |
| Вхождение | Конкретная дата плановой операции: ожидается, оплачено или пропущено |

## 2. Проекты, участники и доступ

Все данные (справочники, транзакции, планы, лимиты) принадлежат проекту; пользователь видит только проекты, в которых состоит. Так одна модель покрывает и раздельную, и общую бухгалтерию.

- При регистрации (email и пароль, GitHub или Facebook — раздел 12) пользователю создаётся личный проект (`PERSONAL`) с базовой валютой из его настроек.
- Семейный проект (`FAMILY`) создаёт любой пользователь и становится в нём `OWNER`; участники добавляются по email.
- Активный проект хранится в cookie (веб) или в заголовке `X-Project-Id` (API). Переключатель — вверху бокового меню.
- Каждая транзакция хранит `created_by` — кто её внёс. В семейном проекте отчёты фильтруются по участнику.
- Счёт может иметь держателя (`holder_user_id`) — чья это карта; это информация, а не ограничение доступа.

| Роль | Чтение | Запись данных | Справочники и лимиты | Участники и удаление проекта |
| --- | --- | --- | --- | --- |
| OWNER | да | да | да | да |
| EDITOR | да | да | да | нет |
| VIEWER | да | нет | нет | нет |

Проверка: middleware определяет пользователя (сессия или API-токен), активный проект и роль; запросы кроме GET с ролью VIEWER получают 403. Сводный отчёт по нескольким проектам сразу — вне первой версии.

## 3. Справочники

Справочники ведутся в каждом проекте отдельно, ключ — код (`UPPER_SNAKE`, неизменяемый). Записи не удаляются, а архивируются: на архивную запись нельзя сослаться заново, старые ссылки остаются валидными.

**Локализация справочников.** Название каждой записи — валюты, счёта, категории, плана — хранится на трёх языках по правилу раздела 8: оригинал на языке ввода + переводы на ru, en, th. Формы справочников содержат поле оригинала, выбор его языка и три поля переводов; в списках есть отметка «нет перевода на ваш язык». Выпадающие списки в транзакциях, планах и лимитах, дерево категорий и бюджет показывают названия на языке интерфейса.

**Валюты.** Код ISO 4217 (`THB`, `RUB`, `USD`), название, символ, число знаков после запятой. У проекта одна базовая валюта — в ней считается бюджет. Курсы к базовой валюте хранятся по датам; пересчёт операции идёт по курсу на её дату (ближайший предыдущий).

**Счета.** Код, название, тип (`CASH`, `CARD`, `BANK`, `SAVINGS`), валюта, начальный остаток, держатель (необязательно). Текущий остаток = начальный + доходы − расходы по счёту.

**Категории — дерево.** Код, название, тип (`EXPENSE` или `INCOME`), родитель (`parent_code`, пусто у корня), порядок сортировки. Правила:

1. Тип потомка совпадает с типом родителя.
2. Цикл запрещён: родителем нельзя назначить себя или своего потомка.
3. Глубина — до 5 уровней.
4. Архивировать узел можно, только если все его потомки архивные.
5. Операции можно относить к любому узлу, не только к листу: «Еда» без уточнения — тоже факт.

Пример дерева: Жильё → Аренда, Коммуналка → Электричество, Вода; Еда → Продукты, Кафе.

## 4. Транзакции и позиции

Транзакция — это шапка (дата, счёт, тип, описание) и одна или больше позиций; у каждой позиции своя категория и сумма. Сумма транзакции не вводится, а считается как сумма позиций.

Пример: чек из супермаркета на 1 250 ฿ — Продукты 900, Бытовая химия 250, Кафе 100. В бюджете эти 1 250 ฿ разойдутся по трём веткам дерева.

Шапка:

- `occurred_on` — дата операции; `account_code` — счёт; `tx_kind` — `EXPENSE` или `INCOME`.
- Описание на языке ввода + переводы (раздел 8).
- `created_by` — кто внёс; `plan_id + plan_date — какое вхождение плана оплачено этой транзакцией (пусто у обычных операций)`.

Позиция:

- `category_code` — тип категории совпадает с `tx_kind`; `amount` > 0 в валюте счёта; `note` — необязательное уточнение.
- Порядок позиций сохраняется (`position`).

Правила:

1. Минимум одна позиция; все суммы положительные, знак определяет тип транзакции.
2. Изменение транзакции заменяет набор позиций целиком в одной SQL-транзакции.
3. Удаление транзакции, созданной из плана, возвращает вхождение в статус «ожидается» — отдельного статуса «оплачено» в БД нет.
4. Переводы между счетами (`TRANSFER`, два счёта и курс) — следующая версия; в первой переводы вносятся двумя операциями.

## 5. Лимиты по категориям

Лимит ограничивает всё поддерево категории: лимит на «Еду» учитывает траты на «Продукты» и «Кафе». Лимит задаётся на любой узел, в базовой валюте проекта, на период `WEEK`, `MONTH` или `YEAR`, и действует с даты `valid_from` до следующего лимита этой категории.

Как считается каждый узел за выбранный период:

- **Факт** — сумма позиций узла и всех его потомков, пересчитанная в базовую валюту.
- **План** — неоплаченные вхождения плановых операций узла и потомков в этом периоде, включая просроченные.
- **Прогноз** = факт + план.
- **Остаток** = лимит − прогноз.
- **Доступно** = min(остаток узла, доступно родителя). Если у «Кафе» осталось 2 000 ฿, а у «Еды» 500 ฿, потратить в кафе можно 500 ฿.

Период отчёта и период лимита могут не совпадать. Тогда лимит пересчитывается по дням: месячный лимит 31 000 ฿ в отчёте за неделю — 7 000 ฿; годовой лимит в отчёте за месяц — лимит × дней в месяце / дней в году.

Предупреждения:

1. Прогноз ≥ 80 % лимита — жёлтый, > 100 % — красный.
2. Сумма лимитов детей больше лимита родителя — предупреждение у родителя: лимиты несогласованы.
3. При вводе позиции, которая выводит узел или его предка за лимит, форма показывает предупреждение, но не запрещает сохранить.

## 6. Плановые и регулярные операции

План описывает ожидаемый расход или доход и правило повторения; транзакция не создаётся, пока пользователь не нажмёт «Оплатил» на конкретной дате в календаре. Разовая плановая операция — это план с правилом `ONCE`.

Поля плана: название (с переводами), тип `EXPENSE`/`INCOME`, счёт, категория, ожидаемая сумма, правило повторения, дата начала, необязательная дата окончания, флаг «активен».

| Правило | Пример | Как считаются даты |
| --- | --- | --- |
| ONCE | Страховка 12.11 | только дата начала |
| DAILY × N | каждый день | начало + k·N дней |
| WEEKLY × N | каждую 2-ю пятницу | начало + k·N недель |
| MONTHLY × N | аренда 5-го числа | день месяца из даты начала; 31-е → последний день короткого месяца |
| YEARLY × N | налог на авто 1 марта | день и месяц из даты начала |

Вхождения вычисляются из правила на лету для видимого периода. Оплату хранит сама транзакция: у неё есть `plan_id` и `plan_date`, и вхождение считается оплаченным, пока такая транзакция существует. Отдельно хранятся только пропуски (`SKIPPED`). Так оплата пишется одной записью, а отмена — это просто удаление транзакции.

Подтверждение оплаты:

1. Клик по вхождению в календаре открывает форму, заполненную из плана: дата оплаты (сегодня), счёт, категория, сумма, описание.
2. Сумму, счёт и дату можно поменять — счёт за электричество каждый месяц разный.
3. «Оплатил» создаёт транзакцию с `plan_id` и `plan_date`. «Пропустить» пишет `SKIPPED` без транзакции.
4. Отмена: удаление транзакции (или снятие пропуска) возвращает вхождение в «ожидается».
5. Повторная оплата того же вхождения запрещена: уникальный индекс по `plan_id`, `plan_date`.

Статусы в календаре: ожидается (серый), просрочено — дата прошла, решения нет (красный), оплачено (зелёный), пропущено (зачёркнуто). Изменение плана влияет только на будущие нерешённые вхождения.

## 7. Бюджет: неделя, месяц, год

Экран «Бюджет» показывает за выбранный период, сколько уже потрачено, сколько ещё предстоит по планам и сколько осталось до лимита — по каждой ветке дерева категорий. Достаточно один раз завести регулярные платежи, и месяц виден целиком ещё до первой оплаты.

- Период: неделя (пн–вс), месяц, год; стрелки «назад/вперёд», кнопка «сегодня».
- Шапка: доходы (факт + план), расходы (факт + план), итог периода, остатки по счетам на конец периода.
- Таблица расходов — дерево, свёрнутое до 2-го уровня; колонки: категория, лимит, факт, план, прогноз, доступно, полоса заполнения с цветом из раздела 5.
- Таблица доходов — то же дерево доходов без лимитов: план, факт, разница.
- Фильтр по участнику в семейном проекте: факт только его операций; лимиты — общие.
- Суммы в базовой валюте проекта; операции в других валютах пересчитаны по курсу на дату.

Все числа выводятся из транзакций, планов и лимитов при каждом запросе; отдельных таблиц с итогами нет. Если расчёт станет медленным (больше \~100 тыс. позиций в проекте), добавляется материализованная таблица месячных сумм по категориям.

## 8. Три языка: ru, en, th

Текст вводится на любом из трёх языков, язык ввода запоминается, переводы на два других добавляются позже и необязательны. Пока перевода нет, показывается оригинал.

Переводимые поля: название валюты, счёта, категории, плана; описание транзакции. Для каждого поля `X` хранится:

| Колонка | Обязательна | Смысл |
| --- | --- | --- |
| `X` | да | текст в оригинале, как ввёл пользователь |
| `X_lang` | да | язык оригинала: `ru`, `en`, `th` |
| `X_ru`, `X_en`, `X_th` | нет | переводы; колонка языка оригинала не заполняется |

Показ на языке L: если L = `X_lang` → `X`; иначе `X_L`, а если он пуст — `X` с пометкой языка оригинала.

Три фиксированных языка — поэтому колонки, а не JSONB: их видно в схеме, по ним просто искать и фильтровать «без перевода на th». Четвёртый язык — это миграция с тремя-пятью `ALTER TABLE`, что приемлемо.

Интерфейс:

- Язык интерфейса: настройка пользователя → cookie → `Accept-Language` → `ru`. Переключатель RU · EN · TH — внизу бокового меню и в шапке лендинга.
- Строки интерфейса — словари в коде (ядро + каждая фича своё), проверка полноты переводов — тестом.
- У транзакции кнопка «Перевод» открывает форму из трёх полей; в списке — фильтр «нет перевода на мой язык».
- Даты — григорианский календарь во всех языках; буддийский год для th — в следующей версии.

## 9. Интерфейс и дизайн-система

Интерфейс — спокойный и плотный, как у рабочего инструмента: меню слева, одна главная кнопка «+ Расход», нейтральная палитра; цвет означает смысл (доход, просрочка, превышение лимита), а не украшает.

**Каркас приложения**

- Боковое меню слева, 240 px: логотип, переключатель проекта, кнопка «+ Расход», разделы «Обзор» (бюджет), «Операции», «Календарь», «Лимиты»; группа «Справочники» — категории, счета, валюты и курсы; внизу — проекты и участники, язык, профиль и выход.
- Меню сворачивается до иконок (64 px) с подсказками; выбор запоминается на устройстве. При ширине 1024–1279 px меню свёрнуто по умолчанию.
- Телефон (до 768 px): меню скрыто, внизу панель из 4 разделов и круглая кнопка «+» по центру; остальное — в пункте «Ещё».
- Над содержимым — заголовок страницы, для вложенных страниц хлебные крошки, действия страницы справа. Активный раздел меню подсвечен.

**Правила UX**

1. Частые действия — не дальше одного нажатия с любой страницы: добавить расход, переключить проект, перейти к бюджету.
2. У каждого списка и отчёта четыре состояния: загрузка (скелетон), пусто (объяснение + кнопка первого действия), ошибка (что случилось и что сделать), данные.
3. Формы: метки над полями, ошибка — под своим полем и сразу, введённое не теряется; сохранение по Enter; первое поле в фокусе.
4. Удаление и архив — без модальных «Вы уверены?»: действие выполняется, тост 5 секунд с кнопкой «Отменить». Подтверждение только для необратимого (удаление проекта, выход из проекта).
5. Горячие клавиши: N — расход, I — доход, Esc — закрыть, ? — список клавиш.
6. Числа и даты — в формате языка интерфейса, суммы выровнены вправо, валюта рядом с суммой.

**Доступность и качество для продакшена**

- WCAG 2.1 AA: контраст текста ≥ 4.5:1, видимый фокус, вся работа с клавиатуры, цели нажатия на телефоне ≥ 44 px, ошибки форм связаны с полями (aria-describedby).
- Скорость: первый экран ≤ 1 с, CSS ≤ 50 КБ, без JS-фреймворков; частичные обновления — htmx и небольшой собственный JS; основные формы работают и без JS.
- Свои страницы 404 и 500 на трёх языках, favicon и иконки PWA, заголовки безопасности (CSP, HSTS), статика с хешем в имени и долгим кэшем.
- Проверка: Lighthouse ≥ 90 по доступности и производительности на «Обзоре», «Операциях» и лендинге.

## 10. Быстрое добавление расхода

Расход добавляется с любой страницы за три действия — сумма, категория, Enter — и не дольше 5 секунд; остальные поля подставляются сами. Это самая частая операция, поэтому ей отданы главная кнопка и клавиша.

**Точки входа:** кнопка «+ Расход» в боковом меню, клавиша N, круглая «+» на телефоне, «+» в строке категории на «Обзоре» (категория уже выбрана). Форма открывается поверх текущей страницы: на компьютере — диалог, на телефоне — лист снизу. После сохранения пользователь остаётся там же, где был.

| Поле | По умолчанию | Удобство |
| --- | --- | --- |
| Сумма | пусто, фокус сразу | цифровая клавиатура; запятая и точка; простая арифметика «120+45» |
| Категория | не выбрана | 6 чипов — частые категории пользователя за 30 дней; поиск по дереву на любом из трёх языков |
| Счёт | последний использованный этим пользователем в проекте | показана валюта счёта |
| Дата | сегодня | быстрые «Вчера» и «Другая…» |
| Описание | пусто, необязательно | язык оригинала = язык интерфейса |

Поведение:

1. «Разбить на позиции» раскрывает полную форму из раздела 4 в том же окне, введённое сохраняется как первая позиция.
2. Переключатель «Расход / Доход» вверху формы; клавиша I открывает ту же форму сразу на доходе.
3. До сохранения форма показывает, сколько останется доступно в категории с учётом предков, и предупреждает при ≥ 80 % и > 100 % лимита (раздел 5); сохранить можно всегда.
4. Enter — «Сохранить», Ctrl/Cmd+Enter — «Сохранить и добавить ещё» (счёт и дата сохраняются), Esc — закрыть.
5. После сохранения — тост «Расход 250 ฿ · Кафе — Отменить» на 5 секунд; цифры текущей страницы (бюджет, список операций, остатки) обновляются без перезагрузки.
6. Роль VIEWER кнопку не видит.

API: `GET /api/transactions/quick-defaults` — счёт по умолчанию, частые категории и остатки лимитов по ним; сохранение — обычный `POST /api/transactions`. Частые категории и счёт вычисляются из позиций транзакций — новых таблиц нет.

## 12. Вход и регистрация через Rauthy

Вход, регистрацию, сброс пароля, вход через GitHub и Facebook и второй фактор делает Rauthy — отдельный сервер входа (OpenID Connect) на Rust. Приложение не хранит пароли и не обрабатывает вход само: оно получает от Rauthy подтверждённого пользователя и создаёт свою сессию. Тот же Rauthy потом даёт единый вход в другие проекты.

&#91;embedded content: вход через Rauthy · что делает Rauthy и что приложение\]

**Как проходит вход**

1. «Войти» или «Создать бюджет» → `GET /auth/login` → переход в Rauthy (authorization code + PKCE S256, `state` и `nonce` в подписанной cookie на 10 минут).
2. На странице Rauthy: email и пароль, кнопки GitHub и Facebook, регистрация, «Забыли пароль». Привязку GitHub и Facebook к аккаунту ведёт Rauthy.
3. Если включён второй фактор, Rauthy отправляет 6-значный код на email и проверяет его (раздел 13).
4. Rauthy возвращает на `/auth/callback`; приложение обменивает код на токены и проверяет ID-токен: подпись по ключам Rauthy (JWKS), `iss`, `aud`, `nonce`, срок.
5. Пользователь ищется по `sub` в `fb_users`. Нет — создаётся и проходит онбординг: имя, базовая валюта, язык, затем личный проект (раздел 2). Email и имя обновляются из токена при каждом входе.
6. Создаётся сессия приложения (раздел 13); токены Rauthy не хранятся. «Выйти» завершает сессию приложения и сессию Rauthy (`end_session_endpoint`).

**Настройка Rauthy**

| Что | Значение |
| --- | --- |
| Развёртывание | контейнер `rauthy` (версия ≥ 0.37) в `compose.yaml`; база — отдельная БД `rauthy` в нашем PostgreSQL; адрес `auth.<домен>` |
| Клиент | `family-budget`, конфиденциальный; authorization code + PKCE S256; redirect `https://<домен>/auth/callback`, после выхода — `https://<домен>/`; scopes `openid email profile` |
| Регистрация | открытая; кнопка «Создать бюджет» ведёт сразу на страницу регистрации Rauthy |
| GitHub, Facebook | внешние провайдеры (Upstream Auth Providers) в админке Rauthy; ключи приложений GitHub и Facebook — там же |
| Второй фактор | раздел `[otp]`: email-коды включены, длина 6 |
| Оформление | логотип, favicon и цвета клиента под дизайн-систему (раздел 9) |
| Письма | SMTP Rauthy; шаблоны регистрации, сброса пароля и кода — на ru, en, th |

Проверить на стенде до начала разработки — в описании Rauthy это не подтверждено:

- [ ] вход через Facebook как внешний провайдер Rauthy;
- [ ] страницы Rauthy на русском и тайском (если перевода нет — добавить свои переводы в Rauthy);
- [ ] email-код включается для отдельного пользователя и отражается в ID-токене как второй фактор (claim `amr`);
- [ ] лимиты попыток и срок жизни email-кода.

## 13. Безопасность

Цель — уровень 2 OWASP ASVS: приложение устойчиво к типовым атакам из OWASP Top 10, а утечка базы не раскрывает пароли, секреты 2FA и токены. Каждая мера ниже обязательна и проверяется тестом или сканером перед релизом.

### Двухфакторная аутентификация

Второй фактор — 6-значный код, который Rauthy присылает на email после пароля или входа через GitHub и Facebook (есть в Rauthy с версии 0.37). Ввод и проверка кода — на странице Rauthy; приложение получает уже проверенный вход.

1. Включение: в конфиге Rauthy раздел `[otp]` с email-кодами длиной 6. Из «Профиль → Безопасность» ведёт ссылка в личный кабинет Rauthy, где пользователь управляет паролем, вторым фактором и привязками GitHub и Facebook.
2. Если у пользователя есть passkey (отпечаток, Face ID), Rauthy сначала предлагает его, код по email — запасной вариант.
3. Владелец семейного проекта может потребовать 2FA от участников. Приложение проверяет признак второго фактора в ID-токене (`amr`) и без него показывает просьбу включить 2FA вместо данных проекта.
4. Срок жизни кода, лимит попыток и защита от подбора — на стороне Rauthy; значения фиксируются после проверки на стенде (раздел 12).

Ограничение: код по email не защищает, если взломана сама почта: через неё можно и сбросить пароль, и получить код. Поэтому в профиле рекомендуем добавить passkey. Когда Rauthy добавит коды из приложения-аутентификатора (заявлены как план), их включаем в Rauthy без изменений в приложении.

### Меры защиты

| Угроза | Меры |
| --- | --- |
| Подбор и утёкшие пароли | пароли, политика паролей и защита от подбора — в Rauthy; политика: ≥ 10 символов; приложение паролей не видит и не хранит |
| Подмена входа (OIDC) | authorization code + PKCE S256; проверка `state`, `nonce`, подписи ID-токена по JWKS, `iss`, `aud`, срока; redirect URI зафиксирован в Rauthy |
| Кража сессии | серверные сессии вместо JWT: случайный id 256 бит в cookie `__Host-session` (HttpOnly, Secure, SameSite=Lax), в БД — хеш; неактивность ≤ 7 дней, жизнь ≤ 30 дней; новый id при каждом входе; список устройств и «Выйти везде»; выход завершает и сессию Rauthy |
| Подделка запросов (CSRF) | SameSite=Lax + CSRF-токен в каждой форме и htmx-запросе; проверка заголовка Origin для всех запросов, меняющих данные |
| XSS | автоэкранирование Askama, фильтр `safe` для пользовательских данных запрещён; CSP без `unsafe-inline` и `unsafe-eval`, скрипты — файлы со своего домена, без CDN |
| Доступ к чужим данным (IDOR) | каждый запрос к БД фильтруется по `project_id` из `Scope`; роль проверяется на сервере, а не скрытием кнопок; для каждой фичи тест «чужой проект → 404» |
| SQL-инъекции | только параметризованные запросы sqlx; склейка SQL из ввода запрещена и проверяется на ревью |
| Утечка БД или логов | в БД приложения нет паролей; id сессий и API-токены — только хеши; секрет клиента Rauthy — в окружении; в логах нет токенов, кодов и cookie |
| Перегрузка и злоупотребление | тело запроса ≤ 64 КБ, таймаут 15 с, страница API ≤ 200 записей, лимит запросов на сессию и API-токен |
| Перехват трафика | только HTTPS для приложения и Rauthy, HSTS (1 год, includeSubDomains), TLS 1.2+ на обратном прокси; CORS только для своего домена (в текущем демо разрешён любой домен — исправить) |
| Встраивание в чужие сайты | `frame-ancestors 'none'`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` с запретом камеры, микрофона и геолокации |
| Уязвимые зависимости | `cargo audit` и `cargo deny` в CI на каждый PR; Renovate для обновлений, включая образ Rauthy; сканирование образов (Trivy); контейнеры без root |
| Клиенты без браузера (macOS-синхронизация, Telegram-бот) | личные API-токены приложения вместо пароля: права (например, `transactions:write`), один проект, срок; токен показывается один раз, в БД — хеш; отзыв в профиле |

### Эксплуатация

- Секреты (секрет клиента Rauthy, ключ подписи cookie, ключи GitHub и Facebook, SMTP) — только из окружения или файлов секретов, не в репозитории и не в образе. Без них или со значениями по умолчанию приложение в продакшене не стартует.
- Админка Rauthy доступна только администратору, с обязательным вторым фактором (passkey).
- В продакшене выключены Swagger `/docs` и демо-данные (`SEED_DEMO`); демо для гостей — отдельный проект с ролью VIEWER.
- БД недоступна снаружи; приложение и Rauthy работают под разными пользователями БД без прав суперпользователя.
- Резервные копии обеих БД (`family_budget` и `rauthy`) ежедневно, зашифрованные, хранятся 30 дней; восстановление проверяется раз в месяц.
- Журнал безопасности приложения: входы, участники и роли, API-токены, удаление данных; хранится 1 год, свои события пользователь видит в профиле. События входа и 2FA ведёт Rauthy.
- Удаление аккаунта удаляет личные данные в приложении и пользователя в Rauthy (PDPA Таиланда и GDPR); семейные проекты остаются у других участников, если есть второй владелец.

### Проверка перед релизом

- [ ] Чек-лист OWASP ASVS уровня 2: аутентификация, сессии, контроль доступа, проверка ввода.
- [ ] OWASP ZAP (baseline) в CI без предупреждений уровней High и Medium.
- [ ] Заголовки безопасности — оценка A или выше в Mozilla Observatory.
- [ ] Тесты изоляции проектов и ролей для каждой фичи; тесты входа по OIDC: неверный state и nonce, чужой aud, просроченный токен → отказ.
- [ ] `cargo audit` без известных уязвимостей.

Вход: `POST /api/auth/login` убирается, клиенты используют API-токен из профиля (`Authorization: Bearer`); проект — заголовок `X-Project-Id`.

Аутентификация: вход и регистрация — Rauthy (раздел 12), приложение — OIDC-клиент (крейт `openidconnect`). В вебе — серверные сессии в cookie, для API и клиентов без браузера — личные API-токены (раздел 13). Оба пути дают фичам один и тот же `Scope { user_id, project_id, role }`. В `compose.yaml` добавляется контейнер `rauthy`; для локальной разработки — его заранее настроенная копия с демо-пользователями.

Интерфейс: общий каркас (боковое меню, диалог быстрого расхода, тосты) живёт в ядре (`kernel/templates`); фичи добавляют пункт меню с иконкой и группой (основное / справочники). Частичные обновления — htmx: сервер возвращает фрагменты Askama. Лендинг и правовые страницы — отдельная фича `site` без таблиц.

## 16. Демо, этапы и приёмка

Текущее демо реализует разделы 2–8 и 14, кроме пунктов ниже; разделы 9–13 добавлены в ТЗ 13.10.2026 и в демо ещё не реализованы; 72 теста домена и use cases проходят без БД, все страницы проверены на ru, en, th. Демо-данные: семейный проект «Семья» (Алексей — OWNER, Anna — EDITOR, язык th), 4 счёта в THB и USD, курсы, лимиты, 8 плановых операций, два месяца операций с многострочными чеками.

Не вошло в демо:

- переводы между счетами (`TRANSFER`);
- переводы примечаний к позициям и названия проекта;
- сообщения валидации на трёх языках — сейчас только на русском;
- Telegram-бот.

Критерии приёмки:

- [ ] Пользователь без членства в проекте не видит его данных ни в интерфейсе, ни в API.
- [ ] VIEWER получает 403 на любое изменение и не видит кнопок изменения.
- [ ] Сумма транзакции равна сумме позиций; позиция с категорией другого типа отклоняется.
- [ ] Категорию нельзя перенести в собственного потомка, глубина ≤ 5.
- [ ] Аренда 5-го числа видна в календаре на 12 месяцев вперёд; «Оплатил» создаёт одну транзакцию, повторная оплата отклоняется, удаление транзакции возвращает «ожидается».
- [ ] Месячный лимит 31 000 в недельном бюджете показывается как 7 000; расход в «Кафе» уменьшает «доступно» у «Еды».
- [ ] Описание, введённое на тайском, показывается на русском после добавления перевода и до него — в оригинале с пометкой.
- [ ] Типичный расход (сумма, частая категория, Enter) добавляется с любой страницы за ≤ 5 с без перехода; «Отменить» в тосте его удаляет.
- [ ] На компьютере меню слева и сворачивается, на телефоне — нижняя панель с «+»; вся навигация доступна с клавиатуры.
- [ ] Гость на `/` видит лендинг на языке браузера; вошедший попадает на «Обзор».
- [ ] Первый вход через Rauthy (пароль, GitHub или Facebook) создаёт пользователя с личным проектом, повторный — находит его же.
- [ ] Facebook-аккаунт с email существующего пользователя не получает доступа к его данным, пока тот не войдёт прежним способом и не привяжет его.
- [ ] Lighthouse ≥ 90 по доступности и производительности на лендинге, «Обзоре» и «Операциях».

* [ ] При включённой 2FA вход без 6-значного кода из письма невозможен; в проекте с «Требовать 2FA» участник без второго фактора не видит данных.
* [ ] Приложение не хранит паролей; «Выйти» завершает и сессию приложения, и сессию Rauthy.
* [ ] Проверки стенда Rauthy из раздела 12 и «Проверка перед релизом» из раздела 13 выполнены.
