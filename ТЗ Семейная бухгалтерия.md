# ТЗ: Семейная бухгалтерия

Oct 9, 2026 · @Aleksey

## 1. Назначение и термины

Система ведёт личную и семейную бухгалтерию нескольких людей: учёт счетов и транзакций, планирование регулярных платежей и контроль лимитов по дереву категорий. Интерфейс и описания транзакций — на ru, en, th.

Цели первой версии:

1. Несколько пользователей ведут общий и раздельные бюджеты без дублирования справочников.
2. Одна покупка (чек) раскладывается на позиции с разными категориями.
3. Регулярные платежи видны в календаре заранее; транзакция появляется только после подтверждения оплаты.
4. Бюджет на неделю, месяц и год показывает план, факт и лимит по каждой ветке категорий.

| Термин | Значение |
| --- | --- |
| Проект | Бюджет, к которому привязаны люди, счета, категории и транзакции. Личный — один участник, семейный — несколько |
| Участник | Пользователь в проекте с ролью owner, editor или viewer |
| Транзакция | Шапка операции: дата, счёт, тип, описание. Сумма = сумма позиций |
| Позиция | Строка транзакции: сумма, категория, своё описание |
| Лимит | Предел расходов категории за период; действует на всё поддерево |
| Плановая операция | Шаблон расхода или дохода с правилом повторения; порождает вхождения в календаре |
| Вхождение | Конкретная дата плановой операции: ожидается, оплачено или пропущено |

## 2. Проекты, участники и доступ

Все данные (справочники, транзакции, планы, лимиты) принадлежат проекту; пользователь видит только проекты, в которых состоит. Так одна модель покрывает и раздельную, и общую бухгалтерию.

- При регистрации пользователю создаётся личный проект (`PERSONAL`) с базовой валютой из его настроек.
- Семейный проект (`FAMILY`) создаёт любой пользователь и становится в нём `OWNER`; участники добавляются по email.
- Активный проект хранится в cookie (веб) или в заголовке `X-Project-Id` (API). Переключатель — в шапке интерфейса.
- Каждая транзакция хранит `created_by` — кто её внёс. В семейном проекте отчёты фильтруются по участнику.
- Счёт может иметь держателя (`holder_user_id`) — чья это карта; это информация, а не ограничение доступа.

| Роль | Чтение | Запись данных | Справочники и лимиты | Участники и удаление проекта |
| --- | --- | --- | --- | --- |
| OWNER | да | да | да | да |
| EDITOR | да | да | да | нет |
| VIEWER | да | нет | нет | нет |

Проверка: middleware определяет пользователя (JWT), активный проект и роль; запросы кроме GET с ролью VIEWER получают 403. Сводный отчёт по нескольким проектам сразу — вне первой версии.

## 3. Справочники

Справочники ведутся в каждом проекте отдельно, ключ — код (`UPPER_SNAKE`, неизменяемый). Записи не удаляются, а архивируются: на архивную запись нельзя сослаться заново, старые ссылки остаются валидными.

**Локализация справочников.** Название каждой записи — валюты, счёта, категории, плана — хранится на трёх языках по правилу раздела 8: оригинал на языке ввода + переводы на ru, en, th. Формы справочников содержат поле оригинала, выбор его языка и три поля переводов; в списках есть отметка «нет перевода на ваш язык». Выпадающие списки в транзакциях, планах и лимитах, дерево категорий и бюджет показывают названия на языке интерфейса.

**Валюты.** Код ISO 4217 (`THB`, `RUB`, `USD`), название, символ, число знаков после запятой. У проекта одна базовая валюта — в ней считается бюджет. Курсы к базовой валюте хранятся по датам; пересчёт операции идёт по курсу на её дату (ближайший предыдущий).

**Счета.** Код, название, тип (`CASH`, `CARD`, `BANK`, `SAVINGS`), валюта, начальный остаток, держатель (необязательно). Текущий остаток = начальный + доходы − расходы по счёту.

**Категории — дерево.** Код, название, тип (`EXPENSE` или `INCOME`), родитель (`parent_code`, пусто у корня), порядок сортировки. Правила:

1. Тип потомка совпадает с типом родителя.
2. Цикл запрещён: родителем нельзя назначить себя или своего потомка.
3. Глубина — до 5 уровней.
4. Архивировать узел можно, только если все его потомки архивные.
5. Операции можно относить к любому узлу, не только к листу: «Еда» без уточнения — тоже факт.

Пример дерева: Жильё → Аренда, Коммуналка → Электричество, Вода; Еда → Продукты, Кафе.

## 4. Транзакции и позиции

Транзакция — это шапка (дата, счёт, тип, описание) и одна или больше позиций; у каждой позиции своя категория и сумма. Сумма транзакции не вводится, а считается как сумма позиций.

Пример: чек из супермаркета на 1 250 ฿ — Продукты 900, Бытовая химия 250, Кафе 100. В бюджете эти 1 250 ฿ разойдутся по трём веткам дерева.

Шапка:

- `occurred_on` — дата операции; `account_code` — счёт; `tx_kind` — `EXPENSE` или `INCOME`.
- Описание на языке ввода + переводы (раздел 8).
- `created_by` — кто внёс; `plan_id + plan_date — какое вхождение плана оплачено этой транзакцией (пусто у обычных операций)`.

Позиция:

- `category_code` — тип категории совпадает с `tx_kind`; `amount` > 0 в валюте счёта; `note` — необязательное уточнение.
- Порядок позиций сохраняется (`position`).

Правила:

1. Минимум одна позиция; все суммы положительные, знак определяет тип транзакции.
2. Изменение транзакции заменяет набор позиций целиком в одной SQL-транзакции.
3. Удаление транзакции, созданной из плана, возвращает вхождение в статус «ожидается» — отдельного статуса «оплачено» в БД нет.
4. Переводы между счетами (`TRANSFER`, два счёта и курс) — следующая версия; в первой переводы вносятся двумя операциями.

## 5. Лимиты по категориям

Лимит ограничивает всё поддерево категории: лимит на «Еду» учитывает траты на «Продукты» и «Кафе». Лимит задаётся на любой узел, в базовой валюте проекта, на период `WEEK`, `MONTH` или `YEAR`, и действует с даты `valid_from` до следующего лимита этой категории.

Как считается каждый узел за выбранный период:

- **Факт** — сумма позиций узла и всех его потомков, пересчитанная в базовую валюту.
- **План** — неоплаченные вхождения плановых операций узла и потомков в этом периоде, включая просроченные.
- **Прогноз** = факт + план.
- **Остаток** = лимит − прогноз.
- **Доступно** = min(остаток узла, доступно родителя). Если у «Кафе» осталось 2 000 ฿, а у «Еды» 500 ฿, потратить в кафе можно 500 ฿.

Период отчёта и период лимита могут не совпадать. Тогда лимит пересчитывается по дням: месячный лимит 31 000 ฿ в отчёте за неделю — 7 000 ฿; годовой лимит в отчёте за месяц — лимит × дней в месяце / дней в году.

Предупреждения:

1. Прогноз ≥ 80 % лимита — жёлтый, > 100 % — красный.
2. Сумма лимитов детей больше лимита родителя — предупреждение у родителя: лимиты несогласованы.
3. При вводе позиции, которая выводит узел или его предка за лимит, форма показывает предупреждение, но не запрещает сохранить.

## 6. Плановые и регулярные операции

План описывает ожидаемый расход или доход и правило повторения; транзакция не создаётся, пока пользователь не нажмёт «Оплатил» на конкретной дате в календаре. Разовая плановая операция — это план с правилом `ONCE`.

Поля плана: название (с переводами), тип `EXPENSE`/`INCOME`, счёт, категория, ожидаемая сумма, правило повторения, дата начала, необязательная дата окончания, флаг «активен».

| Правило | Пример | Как считаются даты |
| --- | --- | --- |
| ONCE | Страховка 12.11 | только дата начала |
| DAILY × N | каждый день | начало + k·N дней |
| WEEKLY × N | каждую 2-ю пятницу | начало + k·N недель |
| MONTHLY × N | аренда 5-го числа | день месяца из даты начала; 31-е → последний день короткого месяца |
| YEARLY × N | налог на авто 1 марта | день и месяц из даты начала |

Вхождения вычисляются из правила на лету для видимого периода. Оплату хранит сама транзакция: у неё есть `plan_id` и `plan_date`, и вхождение считается оплаченным, пока такая транзакция существует. Отдельно хранятся только пропуски (`SKIPPED`). Так оплата пишется одной записью, а отмена — это просто удаление транзакции.

Подтверждение оплаты:

1. Клик по вхождению в календаре открывает форму, заполненную из плана: дата оплаты (сегодня), счёт, категория, сумма, описание.
2. Сумму, счёт и дату можно поменять — счёт за электричество каждый месяц разный.
3. «Оплатил» создаёт транзакцию с `plan_id` и `plan_date`. «Пропустить» пишет `SKIPPED` без транзакции.
4. Отмена: удаление транзакции (или снятие пропуска) возвращает вхождение в «ожидается».
5. Повторная оплата того же вхождения запрещена: уникальный индекс по `plan_id`, `plan_date`.

Статусы в календаре: ожидается (серый), просрочено — дата прошла, решения нет (красный), оплачено (зелёный), пропущено (зачёркнуто). Изменение плана влияет только на будущие нерешённые вхождения.

## 7. Бюджет: неделя, месяц, год

Экран «Бюджет» показывает за выбранный период, сколько уже потрачено, сколько ещё предстоит по планам и сколько осталось до лимита — по каждой ветке дерева категорий. Достаточно один раз завести регулярные платежи, и месяц виден целиком ещё до первой оплаты.

- Период: неделя (пн–вс), месяц, год; стрелки «назад/вперёд», кнопка «сегодня».
- Шапка: доходы (факт + план), расходы (факт + план), итог периода, остатки по счетам на конец периода.
- Таблица расходов — дерево, свёрнутое до 2-го уровня; колонки: категория, лимит, факт, план, прогноз, доступно, полоса заполнения с цветом из раздела 5.
- Таблица доходов — то же дерево доходов без лимитов: план, факт, разница.
- Фильтр по участнику в семейном проекте: факт только его операций; лимиты — общие.
- Суммы в базовой валюте проекта; операции в других валютах пересчитаны по курсу на дату.

Все числа выводятся из транзакций, планов и лимитов при каждом запросе; отдельных таблиц с итогами нет. Если расчёт станет медленным (больше \~100 тыс. позиций в проекте), добавляется материализованная таблица месячных сумм по категориям.

## 8. Три языка: ru, en, th

Текст вводится на любом из трёх языков, язык ввода запоминается, переводы на два других добавляются позже и необязательны. Пока перевода нет, показывается оригинал.

Переводимые поля: название валюты, счёта, категории, плана; описание транзакции. Для каждого поля `X` хранится:

| Колонка | Обязательна | Смысл |
| --- | --- | --- |
| `X` | да | текст в оригинале, как ввёл пользователь |
| `X_lang` | да | язык оригинала: `ru`, `en`, `th` |
| `X_ru`, `X_en`, `X_th` | нет | переводы; колонка языка оригинала не заполняется |

Показ на языке L: если L = `X_lang` → `X`; иначе `X_L`, а если он пуст — `X` с пометкой языка оригинала.

Три фиксированных языка — поэтому колонки, а не JSONB: их видно в схеме, по ним просто искать и фильтровать «без перевода на th». Четвёртый язык — это миграция с тремя-пятью `ALTER TABLE`, что приемлемо.

Интерфейс:

- Язык интерфейса: настройка пользователя → cookie → `Accept-Language` → `ru`. Переключатель RU · EN · TH в шапке.
- Строки интерфейса — словари в коде (ядро + каждая фича своё), проверка полноты переводов — тестом.
- У транзакции кнопка «Перевод» открывает форму из трёх полей; в списке — фильтр «нет перевода на мой язык».
- Даты — григорианский календарь во всех языках; буддийский год для th — в следующей версии.

## 10. Архитектура, экраны и API

Сервер — один бинарник на Rust: Axum 0.8, Askama 0.16 (серверные шаблоны), sqlx 0.8 + PostgreSQL, Tailwind CSS 3, Swagger через utoipa. Структура — эталон rust-hex-api: одна фича = один крейт со своими миграциями, REST, страницами и тестами; фичи не импортируют друг друга, связи — через порты и адаптеры в `crates/app/src/wiring`.

| Экран | URL | Что делает |
| --- | --- | --- |
| Вход, регистрация | `/login`, `/register` | при регистрации создаётся личный проект со справочниками |
| Бюджет | `/budget?view=week\|month\|year` | раздел 7; стартовая страница |
| Календарь | `/planning` | месяц сеткой, клик по вхождению → «Оплатил» / «Пропустить» |
| Плановые операции | `/planning/plans` | список, создание, остановка |
| Операции | `/transactions` | месяц, фильтры по счёту, участнику, «без перевода»; форма с позициями; перевод |
| Лимиты | `/limits` | дерево категорий, история лимитов |
| Категории, счета, валюты, курсы | `/categories`, `/accounts`, `/currencies`, `/rates` | справочники с переводами |
| Проекты и участники | `/projects` | создание проекта, приглашение по email, роли, переключение |

REST — те же сценарии под `/api/<фича>`: справочники (CRUD по коду, DELETE = архив), `/api/transactions` (+ `PUT /{id}/translation`), `/api/planning/plans`, `/api/planning/occurrences?from&to`, `/api/budget?view&date&member`. Вход: `POST /api/auth/login` → JWT; проект — заголовок `X-Project-Id`.

Аутентификация в первой версии — свой JWT (HS256) в cookie или заголовке. Переход на Rauthy меняет только проверку токена в ядре и регистрацию в фиче `projects`; остальные фичи получают тот же `Scope { user_id, project_id, role }`.

## 11. Демо, этапы и приёмка

Демо реализует разделы 2–9 целиком, кроме пунктов ниже; 72 теста домена и use cases проходят без БД, все страницы проверены на ru, en, th. Демо-данные: семейный проект «Семья» (Алексей — OWNER, Anna — EDITOR, язык th), 4 счёта в THB и USD, курсы, лимиты, 8 плановых операций, два месяца операций с многострочными чеками.

Не вошло в демо:

- предупреждение о превышении лимита прямо в форме операции (в бюджете есть);
- переводы между счетами (`TRANSFER`);
- переводы примечаний к позициям и названия проекта;
- сообщения валидации на трёх языках — сейчас только на русском;
- Rauthy и Telegram-бот.

| Этап | Содержание | Результат |
| --- | --- | --- |
| 1. Ядро и доступ | проекты, роли, вход, i18n интерфейса | пользователь входит и переключает проекты |
| 2. Справочники | валюты, курсы, счета, дерево категорий с переводами | все справочники на трёх языках |
| 3. Операции | транзакции с позициями, перевод описаний | чек раскладывается по категориям |
| 4. Планы и лимиты | календарь, оплата и пропуск, лимиты на поддерево | регулярные платежи видны заранее |
| 5. Бюджет | неделя / месяц / год, план-факт-лимит, фильтр по участнику | раздел 7 |
| 6. Продакшен | Rauthy, переводы ошибок, TRANSFER, Telegram | раздел 10 |

Критерии приёмки:

- [ ] Пользователь без членства в проекте не видит его данных ни в интерфейсе, ни в API.
- [ ] VIEWER получает 403 на любое изменение.
- [ ] Сумма транзакции равна сумме позиций; позиция с категорией другого типа отклоняется.
- [ ] Категорию нельзя перенести в собственного потомка, глубина ≤ 5.
- [ ] Аренда 5-го числа видна в календаре на 12 месяцев вперёд; «Оплатил» создаёт одну транзакцию, повторная оплата отклоняется, удаление транзакции возвращает «ожидается».
- [ ] Месячный лимит 31 000 в недельном бюджете показывается как 7 000; расход в «Кафе» уменьшает «доступно» у «Еды».
- [ ] Описание, введённое на тайском, показывается на русском после добавления перевода и до него — в оригинале с пометкой.
