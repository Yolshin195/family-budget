# transactions — Транзакции: двойная запись (написана вручную)

Транзакция — шапка + две или больше проводок (ТЗ, раздел 4). Проводка: куда относится (`ACCOUNT` — счёт,
`CATEGORY` — категория, `SYSTEM` — системный счёт `EXCHANGE` «Обмен валют» или `OPENING` «Начальные остатки»),
валюта и сумма со знаком: «+» — счёт пополнился или деньги ушли на категорию расхода, «−» — наоборот.
**Сумма проводок по каждой валюте = 0** — проверяют домен (`check_balanced`) и отложенный триггер БД.

Клиент присылает тип и поля формы, сервер строит проводки (`domain::build`); ответ API всегда содержит проводки.

| Тип | Поля | Проводки |
| --- | --- | --- |
| `EXPENSE` / `INCOME` | счёт, позиции чека, `refund`, `discount_total` (скидка на чек) | счёт ∓ сумма; на каждую позицию проводка на категорию ± сумма позиции (возврат — обратные знаки) |
| `TRANSFER` | счёт списания, счёт зачисления, `amount` (списано всего, с комиссией), `to_amount` (только при разных валютах), комиссия (категория расхода + сумма) | из: −amount; комиссия +fee; в одной валюте — в: +(amount − fee); при обмене — `EXCHANGE` +(amount − fee) и −to_amount, в: +to_amount |
| `OPENING` | счёт, остаток (может быть < 0) | счёт +остаток; `OPENING` −остаток. Один на счёт, ведётся из формы счёта |

**Позиции чека** (`fb_transaction_items`, docs/group-1.md, шаг 2): категория, название, количество × цена − скидка =
сумма > 0 (`round` до точности валюты, половина вверх; присланная сумма с ценой сверяется с допуском в единицу младшего
разряда, иначе `AMOUNT_MISMATCH`). Скидка на чек делится по позициям пропорционально суммам, остаток округления —
самой крупной; не хранится. Правка — по `id` позиции: с `id` — изменить, без — добавить, `remove_item_ids` — удалить;
форма и старый формат `lines` присылают весь чек. Инвариант «позиция ↔ проводка» (`check_items`): у расхода и дохода
каждая проводка `CATEGORY` ссылается на свою позицию (`item_id`), одна на позицию, сумма — ±amount. Шапка хранит
служебные `account_code`, `total`, `refund` (пишет приложение). Ошибки — `Problem` с кодом и текстом на языке
пользователя (техдолг #9).

Курс перевода не хранится: отношение сумм (без комиссии) в направлении, где число > 1, рядом — курс справочника.
Оплата вхождения плана хранится здесь: `plan_id` + `plan_date` (уникальны в проекте; у `OPENING` нет).

Таблицы: `fb_transactions`, `fb_transaction_items`, `fb_postings` (FK на шапку, ON DELETE CASCADE, триггер
`fb_postings_balanced`; `item_id` — FK на позицию). Миграция `double_entry` переносит позиции и начальные остатки
счетов (временная таблица от фичи accounts); `receipt_items` делает из каждой проводки на категорию расхода и дохода
позицию «1 шт» с названием из уточнения.
Порты: `AccountsLookup` (exists, currencies — валюты всех счетов с точностью, choices, titles, infos),
`CategoriesLookup`, `BudgetView` (лимиты и курсы из фичи budget) → `app/wiring/wire_transactions.rs`.
Публичный API для других фич: `lines` (проводки на категории → факты бюджета), `exchange` (курсовая разница),
`balances`, `opening`/`set_opening`, `has_postings` (для счетов), `payments`, `purge_project`, `first_expenses_between`.

Быстрый расход (ТЗ, раздел 10): `GET /api/transactions/quick-defaults?date` — счёт по умолчанию (последний этого
пользователя в расходах и доходах; переводы его не сбивают), последний перевод, частые категории, дерево с поиском,
остатки лимитов, курсы счетов к базовой валюте. Сохранение — обычный `POST /api/transactions` (в т. ч. `TRANSFER`).

REST (`/api/transactions`): GET/POST `/`, GET `/quick-defaults`, GET `/balances?date`, GET/PUT/DELETE `/{id}`,
PUT `/{id}/translation`, POST `/{id}/external-refs`, GET `/external-refs?provider&external_id`. Фильтр списка: `from`,
`to`, `account_code` (выписка), `tx_kind`, `created_by`, `untranslated`, `place_code`, `for_person_code`,
`external_provider`.

**Связи с внешними записями** (`fb_external_refs`, docs/external-refs.md): ключ `(project_id, provider, external_id)` —
одна запись (SMS банка: `imessage`, `message.guid`) даёт не больше одной операции. `POST /` с `external_ref` идемпотентен:
повтор — `200` и прежняя операция, операция удалена — `409 EXTERNAL_REF_DELETED`; связь `CREATED` пишется вместе с
операцией одной SQL-транзакцией. `POST /{id}/external-refs` — связь `MATCHED`, занята другой операцией —
`409 EXTERNAL_REF_TAKEN`. Внешнего ключа на операции нет: связь переживает удаление (и «Отменить» возвращает её),
правка операции её не видит, `purge` стирает. В ленте и карточке — значок «SMS» с подсказкой.
Страницы (`/transactions`): список за месяц (итоги «Доходы / Расходы» — только по категориям; перевод — одна строка
«откуда → куда» с курсом и комиссией), фильтр по счёту — выписка с остатком на начало и нарастающим остатком;
форма «Расход | Доход | Перевод» с возвратом, комиссией и курсом, позициями («× цена» — количество, единица, цена,
скидка; без JS — три строки в запасе, суммы считает сервер) и «Ещё» со скидкой на чек, блок «Проводки» в карточке;
в ленте позиции сгруппированы по категориям («Круассан · 2 шт × 25 − 3 → 47»); «Перевести описание»;
`/transactions/reconcile?account` — «Сверить остаток»: разница — расход или доход на выбранную категорию.

Тесты: `cargo test -p transactions`; с `TEST_DATABASE_URL` те же тесты use cases идут и на PostgreSQL, плюс проверка
миграции позиций на старых данных.
