# Аудит: переход на go-microcore — вход, уведомления, файлы (17.10.2026)

Что нужно, чтобы регистрация и вход пользователей полностью шли через [go-microcore](https://github.com/go-microcore),
а отправку уведомлений и хранение файлов взяли на себя его сервисы.

Проверено: identity-service, auth-service, challenge-service, notification-service — v1.0.0-rc.1 (09.09.2026);
runtime — v1.0.0-beta.1; SDK — v0.6.0 (13.03.2026: репозиторий на GitHub закрыт, код взят из proxy.golang.org).
Код прочитан, но не запускался. Документация microcore.dev 17.10.2026 недоступна: домен не резолвится. Ссылки вида
`identity-service/internal/…:строка` относятся к этим версиям, `crates/…` — к бухгалтерии (коммит fc77324).

## Коротко

1. **«Поменять адрес провайдера» не получится.** go-microcore — это набор gRPC-API без OpenID Connect, OAuth и без
   страниц входа. Регистрацию, вход, второй фактор, восстановление пароля и страницу «Безопасность» бухгалтерия
   рисует сама на трёх языках, а с сервера вызывает identity, challenge и auth (схема BFF). Это самая большая часть
   работы: 3–4 недели.
2. **Пускать go-microcore в продакшен нельзя, пока не исправлены блокеры** (раздел 5). Два из них ведут к захвату
   аккаунта, оба перепроверены по коду:
   - чужой вход по коду на email и смена чужого пароля через уже подтверждённый вызов жертвы;
   - refresh-токен, который принимается как access-токен.

   Кроме того, доступ остаётся после выхода и после удаления аккаунта, защиты от перебора нет, тестов по сути нет.
   Авторы сами пишут в README «Release Candidate — Not Production Ready».
3. **Пользователи потеряют то, что есть сейчас:**
   - passkey;
   - вход через GitHub и Facebook (сейчас его даёт Rauthy);
   - мгновенный выход: access-токен живёт до 15 минут после выхода.

   Кроме того, имя пользователя — только латиница, 3–15 символов, а письма с кодами придут на одном языке для всех.
4. **MCP для claude.ai перестанет работать.** Сервер авторизации для него сейчас — Rauthy, а в go-microcore OAuth
   нет. Решение — свой сервер авторизации OAuth 2.1 внутри бухгалтерии, 1,5–2 недели. От провайдера входа он не
   зависит, поэтому делать его стоит первым.
5. **Уведомления делегировать можно** — это самая готовая часть: email и Telegram, шаблоны, отложенная отправка,
   повторы, журнал доставки. Ограничения:
   - почта уходит только через smtp.bz;
   - у шаблонов нет языков;
   - HTML не экранируется;
   - `chat_id` в Telegram нужно получить самим.

   Работы в бухгалтерии — около 1,5 недели.
6. **Файлы отдать некуда.** Файлового сервиса в go-microcore нет: ни репозитория, ни образа. Остался только
   клиент в старом SDK к API, которого больше нет. Делегировать можно S3-совместимому хранилищу или диску VDS через
   свой порт.
7. **Эксплуатация усложнится.** Вместо одного контейнера Rauthy понадобятся 4 сервиса, Envoy, Redis, брокер и ещё 3
   базы. Health-check, compose и TLS между сервисами нет.

**Рекомендация:**

- **Уже сейчас**, при любом решении по входу:
  - сервер авторизации MCP внутри бухгалтерии;
  - уведомления через notification-service — после решения по почтовому провайдеру и экранированию.
- **Вход переводить только после двух условий:** блокеры 1–6 исправлены с тестами (у автора или в форке), и
  принято решение, отказываемся ли от passkey, GitHub и Facebook. До этого остаёмся на Rauthy.
- **Файлы** — свой порт `FileStore` с адаптером «диск», когда дойдём до фото чека.
- **Если go-microcore не станет общей платформой для нескольких проектов,** перевод входа не окупается: план
  своего сервиса входа (`docs/id-service-prompt.md`) закрывает больше требований.

Общее:

- **Сборка.** В каждом репозитории один коммит (история сжата), автор — «Microcore Platform». Образы
  `microcorelab/*` собраны для amd64 и arm64 на distroless. Release-CI ставит RC-версии тег `latest`
  (`auth-service/.github/workflows/release.yml:76`), поэтому версию надо закреплять по дайджесту.
- **Транспорт.** Наружу сервисы отвечают только по gRPC; HTTP/JSON идёт через Envoy (`grpc_json_transcoder`).
- **Примеры конфигов Envoy — для разработки, не для продакшена:** CORS для любого origin, admin-порт открыт на
  `0.0.0.0:8081`, порты upstream не совпадают с умолчаниями сервисов (`auth-service/envoy.yaml:1-5,25-32,83`).
- **Чего нет:** docker-compose, health-check, rate limit.
- **Тенантов нет.** Пользователи и роли общие на всю установку, `aud` токена жёстко задан как `auth-service`
  (`auth-service/internal/port/outbound/tokens/default.go:12`).

## 2. Вход и регистрация

### 2.1. Как сейчас

- **Провайдер.** Бухгалтерия — OIDC-клиент Rauthy. Порт `IdentityProvider`
  (`crates/features/projects/src/ports.rs:99`), адаптер `RauthyProvider` (`projects/src/adapters/oidc.rs`):
  - code + PKCE S256 + nonce;
  - ID-токен проверяется по JWKS;
  - используются claims `sub`, `email` (обязателен, `oidc.rs:236`), `name`, `picture`, `amr`.
- **Свои сессии, CSRF, роли и API-токены `fbt_` от провайдера не зависят.** С Rauthy бухгалтерию связывают:
  - колонка `fb_users.rauthy_sub` (миграция `20261013111058_rauthy_sessions_tokens_audit`);
  - регистрация — переход на `{issuer}/users/register` (`projects/src/adapters/web.rs:190`);
  - выход — через `end_session_endpoint`;
  - удаление пользователя — `DELETE {issuer}/users/{sub}` по Admin API (`oidc.rs:311`);
  - ссылка «Открыть кабинет Rauthy».
- **2FA.** Значения `amr` превращаются в `fb_sessions.mfa` (`projects/src/domain.rs:228`), а на нём работает
  настройка «Требовать 2FA» в проекте (`kernel/src/auth.rs:244`, `kernel/src/web.rs:270`).
- **MCP.** Сервер авторизации — Rauthy, бухгалтерия — ресурс:
  - метаданные RFC 9728 (`mcp/src/adapters/http.rs:58`);
  - проверка JWT по JWKS, `aud` = `{base}/mcp`;
  - `azp` ищется в `fb_mcp_grants` (`mcp/src/service.rs:174`, `oidc.rs:171-231`).
- **Пользователям сейчас доступны:** пароль, код по email, passkey, вход через GitHub и Facebook
  (`site/content/guides/profile/index.md:23`, `site/content/privacy.md:16`).

### 2.2. Что даёт go-microcore

**Регистрация** (`identity-service/internal/services/signup/service.go`):
- `BeginSignup{username, password, email}` → код на email → `POST /challenge/v1/{id}/verify` → `CompleteSignup`.
- Токенов после регистрации нет: дальше нужен отдельный вход.
- Username проходит через `^[a-zA-Z0-9-]{3,15}$`, пароль — `^[[:graph:]]{8,64}$` (`signup/config.go:24,27`).
- Аккаунт, пароль и канал создаются без общей транзакции: дубль email оставляет «осиротевший» аккаунт
  (`signup/service.go:216-249`).

**Вход** (`signin/service.go`):
- по паролю, или по коду на email (нельзя, если email — единственный способ MFA);
- если у аккаунта есть MFA, первый шаг выдаёт токены с `mfaRequire=true`;
- второй шаг — TOTP, код на email или код в Telegram.

**Восстановление:** по username или email, код уходит на привязанные каналы.

**Токены** выпускает auth-service:
- HS512 с общим секретом (`auth-service/internal/adapter/outbound/tokens/adapter.go:136`);
- `sub` — номер аккаунта (BIGINT);
- `mfaRequire` означает «MFA ещё не пройдена»; `amr`, `auth_time`, email и имени в токене нет;
- access живёт 15 минут, refresh — 15 дней с ротацией;
- сессия — это пара (аккаунт, `device`), где `device` — произвольная строка от клиента.

**Профиль:** username, роли, статус; email и Telegram хранятся как «каналы». Имени, аватара, языка и часового
пояса нет.

**Удаление:** только админское (право `Account/Delete`, у роли `user` его нет), жёсткое, сессии не отзываются.

**Событий нет:** ни «аккаунт создан», ни «аккаунт удалён». Наружу публикуются только команды на отправку
уведомлений.

**Языков нет:**
- шаблоны писем — английские, с брендом «Microcore» (`identity-service/internal/app/seed/templates/`);
- у шаблона нет поля языка, у аккаунта нет языка;
- ошибки приходят кодами (`USERNAME_ALREADY_EXISTS`), их можно перевести у себя.

**Страниц входа нет, OIDC и OAuth тоже.** Поиск по `openid`, `oauth`, `jwks`, `pkce`, `id_token`, `well-known`,
`consent`, `amr` в identity, auth и challenge находит только посторонние совпадения. Passkey/WebAuthn, вход через
соцсети и Telegram Login отсутствуют.

### 2.3. Требования и разрывы

| Нужно бухгалтерии | go-microcore | Что делать |
|---|---|---|
| Стандартный OIDC: при смене провайдера меняется только адрес | Нет ни OIDC, ни страниц | Свои страницы и новый адаптер (п. 2.4) |
| Страницы и письма на ru/en/th | Страниц нет; один шаблон письма на всех, английский | Страницы — у себя через `i18n.rs`. Для писем identity нужна доработка: язык у аккаунта и шаблон на каждый язык. Без неё коды входа придут на одном языке, а это нарушает правило «три языка — всегда» |
| Passkey, вход через GitHub и Facebook (есть сейчас) | Нет | Регрессия для пользователей: либо доработка identity, либо отказ от этих способов |
| Вход через Telegram в один тап (`id-service-prompt.md`) | Telegram — только канал для кодов, `chat_id` вводится вручную | Доработка identity или свой бот (п. 3.4) |
| Имя на любом языке | Username латиницей, 3–15 символов; поля «имя» нет | Имя, аватар, язык и тему хранить в `fb_users` (уже есть); username — технический логин |
| Признак второго фактора для «Требовать 2FA» | Только `mfaRequire` (MFA ещё не пройдена) | BFF знает, прошёл ли второй шаг, и ставит `fb_sessions.mfa = true` только после него |
| Выход и «выйти везде» сразу | `TerminateCurrentSession`/`TerminateAccountSessions` блокируют только обновление токена; access живёт до 15 минут | Хватит, если access-токены microcore не выходят за пределы сервера бухгалтерии: свои сессии гасим сами |
| Удаление аккаунта пользователем | Только админское, жёсткое; доступ сохраняется (блокер 3) | Сервисный токен с `Account/Delete` + `TerminateAccountSessions` токеном пользователя; блокер 3 исправить |
| SSO между проектами | Общих страниц и cookie нет | Без своего фронта входа невозможно |
| Подпись ключевой парой, проверка по JWKS | Общий секрет HS512 без `kid` и ротации; секрет даёт право выпускать любые токены | Секрет бухгалтерии не передавать. Токены получает только сервер бухгалтерии напрямую от identity; подпись не проверяем, `sub` берём из ответа |
| MCP: OAuth 2.1, CIMD, RFC 8707, согласие | Нет | Свой сервер авторизации (п. 2.5) |
| «Приложение не получает паролей» (`site/content/privacy.md:16`) | При BFF пароль проходит через сервер бухгалтерии | Переписать политику на трёх языках; не логировать тела запросов; хранить только токены |

### 2.4. Схема подключения: бухгалтерия как BFF

Браузер ходит только в бухгалтерию; сервер бухгалтерии ходит в go-microcore. Envoy закрыт от интернета. Если
хочется строгой типизации — gRPC через `tonic`, клиенты генерируются из `contract/proto`.

1. **Свои страницы на Askama и `i18n.rs`, с CSRF и лимитами** (в go-microcore лимитов нет):
   - вход по паролю или коду;
   - регистрация в три шага;
   - шаг MFA для TOTP, email и Telegram;
   - восстановление пароля;
   - «Профиль → Безопасность»: смена пароля, настройка TOTP с QR-кодом (QR уже есть у приглашений), каналы email и
     Telegram, удаление.

   Ошибки — коды из `ErrorInfo.reason`, переведённые на три языка.
2. **После входа:**
   - `sub` из ответа сохраняется в `fb_users`, открывается своя `fb_sessions`, как сейчас;
   - refresh-токен microcore хранится в сессии в зашифрованном виде — он нужен для действий на странице
     «Безопасность» от имени пользователя;
   - access-токен получается через `RenewTokens` по мере надобности;
   - `device` = id нашей сессии.
3. **Порт.** `IdentityProvider` устроен вокруг перенаправления и обмена кода, его нужно заменить. Новый порт —
   шаги `begin_*`/`complete_*` для входа, регистрации, MFA и восстановления, плюс `logout`, `delete`, `channels`.
   Адаптер — `MicrocoreProvider`, для тестов — `FakeMicrocore` по образцу `FakeRauthy`
   (`projects/src/tests.rs:41`).
4. **База.** `rauthy_sub` переименовать в `idp_subject` и добавить `idp` (`rauthy` | `microcore`) на время
   переезда. `fb_users.email` оставить `NOT NULL`: в microcore email при регистрации обязателен.
5. **2FA.** `mfa_required.html` и «Безопасность» ведут на свою страницу вместо кабинета Rauthy.
   `update_user_identity` (`projects/src/service.rs:181`) больше не перезаписывает имя при каждом входе: имя теперь
   хранится только у нас.
6. **Выход:** `TerminateCurrentSession` + отзыв своей сессии. Из CSP `form-action` убрать origin Rauthy
   (`kernel/src/web.rs:517`).
7. **Удаление аккаунта:** `delete_account` (`projects/src/service.rs:372`) вместо Admin API Rauthy вызывает
   `TerminateAccountSessions` и `DeleteAccount`.
8. **IP и браузер в списке устройств.** Envoy перезаписывает `x-client-ip` (`identity-service/envoy.yaml:57-66`),
   поэтому microcore увидит IP сервера бухгалтерии. Список устройств показываем свой (`fb_sessions`), а не из
   microcore.
9. **Конфиг:**
   - `MICROCORE_IDENTITY_URL`, `MICROCORE_AUTH_URL`, `MICROCORE_CHALLENGE_URL`;
   - `MICROCORE_SERVICE_TOKEN[_FILE]` — статический токен с минимальными правами;
   - из правила «продакшен не стартует без OIDC» (`kernel/src/config.rs:146`) сделать «без провайдера входа».

### 2.5. MCP

Rauthy сейчас — сервер авторизации для claude.ai. После его отключения подключение коннектора сломается; личные
токены `fbt_` (Claude Code) продолжат работать.

| Вариант | Оценка |
|---|---|
| A. Оставить Rauthy только для MCP | Не годится: аккаунтов в Rauthy после переезда не будет, пользователю понадобится второй вход |
| B. **Сервер авторизации OAuth 2.1 в бухгалтерии** | **Рекомендуется.** Метаданные RFC 8414, `/authorize` (вход — наша сессия, согласие — существующая страница `/assistants` с выбором проекта и прав), `/token` (code + PKCE, ротация refresh), CIMD для claude.ai, `aud` = `{base}/mcp`, ключи EdDSA. Требования — `docs/id-service-prompt.md`, раздел 3. 1,5–2 недели. Работает и с Rauthy, и с go-microcore |
| C. Дописать OAuth в auth-service | Крупная доработка чужого проекта на Go, полный аналог варианта B, только дальше от нас |

### 2.6. Перенос пользователей

Принцип из `docs/id-service-prompt.md`: никакой автосклейки аккаунтов, новый способ входа привязывается только к
уже вошедшему пользователю.

1. На время переезда работают оба провайдера (`fb_users.idp`).
2. Пользователь, вошедший через Rauthy, нажимает «Перейти на новый вход», регистрируется или входит в go-microcore,
   и бухгалтерия записывает новый `sub` к его `fb_users`.
3. Тем, кто входил только через GitHub, Facebook или passkey, придётся завести пароль: в go-microcore других
   способов нет.
4. Когда все перешли, Rauthy выключается. Удалить его базу, бэкапы, `deploy/rauthy/` и настройки Caddy для
   `AUTH_DOMAIN`.

Для семейного масштаба этого достаточно. Массовый импорт через `AccountsService.CreateAccount` возможен, но
пароль пришлось бы задавать через восстановление, а оно сейчас уязвимо (блокер 1).

## 3. Уведомления

### 3.1. Сейчас

Пользователям бухгалтерия ничего не отправляет: ни SMTP, ни Telegram, ни push. Письма шлёт только Rauthy (коды и
сброс пароля), а скрипт деплоя присылает администратору оповещения (`scripts/deploy-vds.sh:771`).

Что могло бы порождать уведомления:
- плановые платежи — статус `Overdue` (`planning/src/domain.rs:223`);
- лимиты — уровни `Warn` от 80 % и `Over` (`budget/src/domain.rs:125`);
- новый участник проекта и приглашения;
- коды входа — если вход переедет в go-microcore, их будет отправлять identity.

В дорожной карте: «Напоминания о плановых платежах и превышении лимита: email, Telegram, push»
(`docs/roadmap.md:134`).

### 3.2. Что даёт notification-service

- **Отправка.** `POST /notification/v1/send/email` и `/send/telegram` с полями `{id, templateId, toEmail | chatId,
  variables, metadata, scheduled}` (`notification-service/contract/proto/microcore/notification/v1/delivery.proto:167-205`).
  - `id` задаёт отправитель — это ключ идемпотентности, повтор с тем же `id` второй раз не отправляется.
  - `scheduled` обязателен; сообщение уйдёт, когда наступит это время.
- **Шаблоны** хранятся в Postgres и управляются через API: папки, шаблон, к нему подшаблоны email (`from`,
  `subject`, `html_body`, `text_body`) и Telegram (`parse_mode`, `message_text`).
- **Доставка:** очередь в Postgres (`FOR UPDATE SKIP LOCKED`). До 5 попыток с линейной паузой; доставка «хотя бы
  один раз» — после сбоя возможен повтор. Журнал событий доставки ведётся.
- **Доступ:** bearer-токен с правом `Delivery/Email/Send` или `Delivery/Telegram/Send`. Для сервиса — статический
  токен из auth-service (`IssueStaticToken`).

### 3.4. Подключение

1. **Новая фича `notifications`** (крейт):
   - исходящая очередь `fb_notifications` (наш UUID = `id` доставки);
   - настройки пользователя: каналы, события, время;
   - привязка Telegram;
   - планировщик в одном экземпляре — advisory lock. Сейчас фоновые циклы идут в каждом экземпляре
     (`crates/app/src/main.rs:100`).
2. **Часовой пояс пользователя** (Ц6 дорожной карты) — чтобы «завтра платёж» считалось по пользователю, а не по
   серверу.
3. **Шаблоны** хранятся в репозитории (`deploy/microcore/templates/<шаблон>.<язык>.*`) и заливаются скриптом через
   `TemplatesService`. Тест проверяет, что у каждого шаблона есть все три языка.
4. **Отправка** — `POST /notification/v1/send/*` с сервисным токеном, у которого есть только права `Send`.
5. **Сайт:** гайд «Уведомления», запись в «Что нового», политика конфиденциальности (smtp.bz, Telegram).

## 4. Файлы

**Делегировать некуда.** Сервиса файлов в go-microcore нет: на GitHub нет репозиториев `files-service`,
`file-service` и `storage-service`, на Docker Hub только четыре образа (identity, auth, challenge, notification).
Остался лишь клиент в SDK v0.6.0 (`sdk/services/files/repository/http`):
- виртуальная файловая система по путям: `POST /files/{path}` (multipart), `GET /files/list/{path}`, скачивание
  через одноразовый токен `GET /files/download/stream/{token}`;
- нет прав доступа, метаданных, ограничений размера и S3;
- API относится к старому `framework v0.15.0`, текущие сервисы его не поддерживают.

**Бухгалтерия сейчас файлов не хранит.** Что в планах:
- фото чека к операции (этап 4) — нужно хранилище;
- импорт выписок CSV/PDF (этап 3) — файл разбирается и не хранится;
- экспорт — генерируется на лету.

**Чему будут мешать загрузки:**
- лимит тела запроса 64 КБ (`kernel/src/auth.rs:42`);
- таймаут 15 секунд (`crates/app/src/main.rs:203`);
- CSP `img-src 'self' data:`;
- `Permissions-Policy: camera=()`.

**Предложение:**
- порт `FileStore` в kernel с методами put, get, delete и presign;
- адаптер «диск»: том на VDS, входит в бэкап;
- адаптер S3 — позже (MinIO или Garage на VDS, либо внешнее хранилище), через крейт `object_store`;
- ключи вида `projects/{project_id}/receipts/{uuid}`, доступ проверяет бухгалтерия по членству в проекте;
- раздача через приложение или короткую presigned-ссылку;
- у фото убирать EXIF, делать превью;
- файлы удаляются вместе с проектом или аккаунтом (срок 30 дней из политики данных);
- отдельный лимит тела запроса для маршрута загрузки.

Около недели вместе с фото чека. Если у go-microcore появится файловый сервис, адаптер к нему встанет за тот же
порт — но ему понадобятся права доступа по проекту, которых в старом API не было.
