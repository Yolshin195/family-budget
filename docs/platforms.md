# Платформы: Telegram, мобильное и десктоп-приложение, офлайн — ТЗ на доработку

21.10.2026. Черновик по итогам обсуждения; дорабатываем по ходу. Основа — идея `site/content/ideas/mobile-app*`,
дорожная карта (`docs/roadmap.md`, этапы 3 и 5) и шаг 4 группы 1 (`docs/group-1.md`). Где этот документ
расходится с дорожной картой, действует он; такие места помечены **Решение**. Всё, что зависит от внешних
сервисов и версий (Dioxus, Telegram Bot API, Google Play, Apple), сверять с актуальной документацией в начале
каждого этапа.

## 1. Цель

Вывести бюджет за пределы браузера: операции записываются там, где они появляются, и без интернета.

- **Telegram:** бот принимает пересланные SMS и скриншоты банка, присылает напоминания; Mini App — бюджет
  внутри Telegram на любом телефоне.
- **Мобильное приложение (Android, затем iPhone):** работает офлайн, само подхватывает операции из уведомлений
  банка и скриншотов в галерее.
- **Десктоп-приложение:** офлайн и локальный MCP — Claude Desktop работает с бюджетом без сервера.
- **Сайт** остаётся и продолжает работать как сейчас.

### 1.1. Не цели

- Отказ от сервера: сервер остаётся главным — права, конфликты, итоговые цифры.
- Полностью «нативный» вид интерфейса: компоненты Dioxus рисуются в webview и выглядят одинаково на всех
  платформах (см. 4.1).
- Чтение уведомлений на iPhone: Apple не даёт это делать ни одному приложению.
- MCP с телефона без сервера: Claude на телефоне подключается только к удалённым MCP-серверам.

## 2. Принципы

1. **Одно ядро, разные сборки.** Правила учёта, сервисы и порты фич — общие для сервера и приложений.
   Сборки отличаются только адаптерами: хранилищем и входами.
2. **Входы тонкие.** Сайт, REST, MCP, Telegram, API синхронизации, экраны приложения — адаптеры: принимают
   запрос, проверяют права, вызывают сервис фичи. Своей логики учёта во входах нет.
3. **Права — в одном месте.** Любой внешний вход — «клиент» с правами и записью в журнале (раздел 6).
   Удаления через ассистентов и бота нет, как сейчас в MCP.
4. **Сервер главный.** Приложение хранит копию и очередь изменений; спорные случаи решает сервер.
5. **Запись — всегда через очередь.** Отдельного пути «есть сеть — сразу на сервер» нет (раздел 10).
6. **Ничего не теряется и не дублируется:** у операции UUID с устройства, `client_id` и `external_ref`
   (раздел 7).
7. **Три языка — сразу.** Экраны, ответы бота, уведомления, ошибки, гайды, «Что нового» — ru/en/th в том же PR
   (CLAUDE.md).
8. **Пользователь сам решает, что разрешить:** доступ к уведомлениям, галерее, Telegram включается вручную и
   отключается в любой момент.

## 3. Целевая архитектура

```
                    ┌──────────── ЯДРО (Rust, без БД и веба) ────────────┐
                    │ фичи: domain + service + ports                    │
                    │ kernel-core: ошибки, i18n, коды, Lang, поиск      │
                    │ sync-protocol: формат синхронизации               │
                    │ import: разбор уведомлений, SMS, чеков, выписок   │
                    └──────────────┬──────────────────────┬─────────────┘
                                   │                      │
        ┌─────────── СЕРВЕР ───────┴─────┐   ┌──── КЛИЕНТЫ (Dioxus) ─────────┐
        │ хранилище: Postgres            │   │ web / telegram: серверные     │
        │ входы:                         │   │   функции (онлайн)            │
        │   • сайт (askama → Dioxus)     │   │ mobile / desktop: SQLite +    │
        │   • REST API                   │   │   очередь синхронизации       │
        │   • API синхронизации ◄────────┼───┤ мостики Kotlin/Swift:         │
        │   • MCP (claude.ai, телефон)   │   │   уведомления, галерея, OCR   │
        │   • Telegram: бот + Mini App   │   │ локальный MCP (desktop)       │
        │ доступ: клиенты и права        │   └───────────────────────────────┘
        └────────────────────────────────┘
```

### 3.1. Устройство репозитория (целевое)

```
crates/
  kernel-core/        без axum и sqlx: error, i18n, code, search, pagination, rates
  kernel/             серверное: web, auth, throttle, undo, config, testing (зависит от kernel-core)
  features/<фича>/    domain, service, ports — всегда; adapters за cargo-features
  features/telegram/  новая фича: бот, привязка, проверка initData
  sync-protocol/      типы и версии протокола синхронизации
  import/             разбор уведомлений, SMS, текста чеков, выписок
  app/                сервер: проводка (wiring), main
client/
  ui/                 общие страницы и компоненты Dioxus
  api/                серверные функции (общие для web и telegram)
  web/                оболочка сайта
  telegram/           оболочка Mini App
  mobile/             оболочка Android/iOS + android/, ios/ (Kotlin/Swift-мостики)
  desktop/            оболочка компьютера + локальный MCP
```

Структура фич задана эталоном `rust-hex-api` (`arch.toml`, версия 2). **Решение:** разделение kernel и
адаптеры за cargo-features вносим в сам эталон (новая версия), чтобы `arch.py upgrade` не откатил изменения.

### 3.2. Cargo-features адаптеров

| Feature | Что включает | Где нужна |
| --- | --- | --- |
| *(без features)* | domain, service, ports, dto | везде, в том числе wasm32 и Android/iOS |
| `postgres` | `adapters/postgres.rs`, sqlx postgres | сервер |
| `web` | `adapters/web.rs`, `adapters/http.rs`, askama, axum, utoipa | сервер |
| `sqlite` | `adapters/sqlite.rs`, sqlx sqlite или rusqlite | mobile, desktop |
| `memory` | `adapters/memory.rs` | тесты, демо |

Сервисы, которым сейчас нужен `kernel::web::Choice` и похожие типы, переводим на типы из `kernel-core`.

## 4. Технологии

### 4.1. Dioxus

**Решение:** клиенты пишем на Dioxus (0.7+). Почему:

- один код интерфейса на Rust — сайт, Telegram Mini App, телефон и компьютер;
- fullstack на axum — тот же стек, что у сервера; роутер Dioxus подключается к нашему axum;
- серверные функции (`#[server]`) — без ручного описания API для онлайн-клиентов;
- общие типы с сервером.

Что учитываем:

- **Компоненты** (dioxuslabs.com/components) — HTML-компоненты в webview, не нативные виджеты. Внешний вид
  одинаковый на всех платформах; системный вид не обещаем.
- **Серверные функции требуют сети.** Офлайн-клиенты (mobile, desktop) работают через локальный слой данных
  (раздел 9.2), а не напрямую через `#[server]`.
- **Мобильная часть Dioxus моложе десктопной.** Своей системы плагинов для нативного кода нет — Kotlin/Swift
  подключаем вручную (JNI / Objective-C). Проверяется пилотом (раздел 13, этап F).
- **Запасной вариант** — Tauri 2 (готовые плагины Kotlin/Swift). Ядро на Rust при переходе не меняется.
- **LiveView** (состояние на сервере, без WASM) не используем: компоненты не переедут в офлайн-клиенты.

### 4.2. Судьба askama и htmx

Дорожная карта (этап 1) оставляет вопрос «решить судьбу htmx». **Решение:** сайт переводим на Dioxus
постепенно, по экрану; askama-страницы живут, пока их экран не переписан. Первые экраны на Dioxus — в Mini
App (`/tg/`), сайт — после пилота. Лендинг и правовые страницы в `crates/features/site` не трогаем (CLAUDE.md).

### 4.3. Хранилище на устройстве

SQLite, шифрование базы (SQLCipher или аналог — выбрать на этапе H), ключ — в Android Keystore / iOS Keychain /
системном хранилище ключей на компьютере. Схема — зеркало нужных таблиц сервера плюс служебные: `outbox`,
`sync_state`, `conflicts` (раздел 10.4).

## 5. Этап A. Ядро без сервера

Цель — фичи собираются без axum и sqlx под `wasm32-unknown-unknown` и `aarch64-linux-android`.

1. Разделить `kernel` на `kernel-core` и `kernel` (раздел 3.1). Переводы (`i18n`) и `Problem` — в `kernel-core`.
2. В каждой фиче: адаптеры за cargo-features (раздел 3.2), `app` включает `postgres` и `web`.
3. Убрать из `domain`/`service` зависимости от веб-типов.
4. CI: джоб `cargo check` ядра под `wasm32-unknown-unknown` и `aarch64-linux-android` без features.
5. Новая версия эталона `rust-hex-api` с этим устройством; `arch.py upgrade` проекта.

**Готово, когда:** `cargo test --workspace` зелёный, сервер работает как раньше, проверка сборки ядра под wasm32
и Android проходит в CI. Пользователь изменений не видит (`Changelog: none`).

## 6. Этап B. Клиенты и права

Сейчас доступ есть только у MCP: `Grant` (пользователь, `client_id` ассистента, проект, права, требование 2FA).
Обобщаем до «клиентов».

### 6.1. Модель

| Поле | Тип | Что |
| --- | --- | --- |
| `id` | UUID | |
| `user_id` | UUID | владелец |
| `project_id` | UUID | проект доступа |
| `kind` | `mcp` \| `telegram` \| `device` | вид клиента |
| `external_id` | TEXT | `client_id` MCP / Telegram user id / id устройства |
| `name` | TEXT | «Claude», «Telegram @nick», «Pixel 8» |
| `permissions` | как у MCP сейчас | права по справочникам и операциям |
| `mfa` | BOOL | открыт со вторым фактором |
| `created_at`, `last_used_at`, `revoked_at` | | |

- Существующие доступы MCP переносятся миграцией без изменений прав.
- Ключ — `(user_id, kind, external_id)`.
- Проверка прав и журнал — общий сервис; MCP переходит на него без изменения поведения.
- Удаление и архив через клиентов — нельзя (как в MCP). Исключение — правка своих операций с устройства,
  у которых есть локальная версия (раздел 10.3).

### 6.2. Интерфейс

Страница «Подключённые приложения» (вместо или рядом с «Подключить Claude»): список клиентов, права, последний
вход, «Отключить». Отключение — сразу: токены клиента перестают работать.

**Готово, когда:** MCP работает через общий слой без изменений для пользователя, тесты прав на PostgreSQL и в
памяти, страница на трёх языках, гайд «Подключить Claude» обновлён и скриншоты пересняты.

## 7. Этап C. Приём операций без дублей

Это шаг 4 группы 1 (`docs/group-1.md`), он ещё не сделан. Без него нельзя ни синхронизацию, ни импорт
уведомлений, ни бота. Делаем по `group-1.md` без изменений:

- `client_id` — уникален в проекте; тот же хеш тела → существующая операция, другой → `409 client_id_conflict`;
- `external_ref` — номер операции банка, id SMS/уведомления; уникален по `(project_id, account_code,
  external_ref)`;
- пакетное создание (REST и MCP), лимит тела 2 МБ;
- `allow_duplicate` — явное согласие на похожую операцию.

**Решение:** UUID операции, созданной на устройстве, генерирует устройство и передаёт как `client_id`.
Повторная отправка той же операции безопасна.

## 8. Этап D. Импорт: разбор уведомлений, SMS и чеков

Новый крейт `import` (в ядре, без БД и сети) и сущность «Входящие» на сервере.

### 8.1. Крейт `import`

- Вход: текст уведомления или SMS (с отправителем и временем), текст со скриншота (уже распознанный OCR на
  устройстве), строки выписки CSV.
- Выход: кандидат операции — вид (расход/доход/перевод), сумма, валюта, счёт (по последним цифрам карты),
  место (по названию продавца, через поиск мест), время, `external_ref`, уверенность и что не распознано.
- Шаблоны банков — данные, а не код: файл на банк (регулярные выражения по языкам уведомлений). Первые:
  KBank, SCB, Bangkok Bank, Т-Банк, Сбер. Добавить банк — добавить файл и тесты на реальных (обезличенных)
  примерах.
- Не распознано — кандидат с пустыми полями и исходным текстом; дальше — пользователь или Claude.
- Сопоставления «карта ••1234 → счёт», «продавец → место» запоминаются после подтверждения.

### 8.2. «Входящие»

Кандидат не становится операцией сам: он попадает во «Входящие» и ждёт подтверждения.

- Источники: бот Telegram, мобильное приложение, MCP (`add_draft` — новый инструмент), позже — выписки.
- Карточка: исходный текст или скриншот, заполненные поля, «Сохранить», «Изменить», «Это не операция».
- «Сохранять сразу» — настройка по источнику и уверенности (по умолчанию выключена).
- Дубль по `external_ref` или похожая операция (сумма, счёт, время ± N минут) — предупреждение, не новая запись.
- Скриншоты хранятся на сервере ограниченное время (срок — открытый вопрос), удаляются вместе с проектом.

**Готово, когда:** крейт с тестами на примерах каждого банка, «Входящие» в сайте, REST и MCP, три языка, гайд.

## 9. Этап E–F. Telegram: бот и Mini App

### 9.1. Бот (фича `telegram`)

- **Webhook** на сервере, секрет вебхука проверяется; токен бота — в секретах, не в репозитории.
- **Привязка аккаунта:** на странице «Подключённые приложения» — «Подключить Telegram» → ссылка
  `t.me/<бот>?start=<одноразовый код>` (10 минут, одно использование) → бот создаёт клиента `kind = telegram`
  с выбранными правами. Вход через OAuth внутри Telegram не используем.
- **Что умеет:**
  - пересланное SMS, текст уведомления, скриншот → разбор (`import`) → карточка во «Входящих» с кнопками
    «Сохранить», «Открыть», «Не операция»;
  - короткий ввод: «250 кофе» → кандидат по частым категориям и местам;
  - напоминания: плановый платёж завтра, лимит ≥ 80 % и > 100 % (пункт дорожной карты этапа 3);
  - `/balance`, `/budget` — коротко, подробнее — в Mini App.
- **Язык** — по `language_code` пользователя Telegram (ru/en/th, остальные — en), можно сменить в настройках.
- **Приватность:** сообщения боту хранятся у Telegram — написать в «Конфиденциальности» на трёх языках.

Связь со своим сервисом входа (`docs/id-service-prompt.md`): вход через Telegram там — отдельная задача.
Когда он появится, привязка бота может опираться на тот же Telegram id.

### 9.2. Mini App на Dioxus

Mini App — страница `/tg/` нашего сервера, которую Telegram открывает по кнопке бота. Это первый клиент на
Dioxus и пилот для мобильного приложения.

**Поток входа:**

1. Telegram открывает `/tg/`; сервер отдаёт HTML (серверный рендер), затем подгружается WASM.
2. Клиент берёт `window.Telegram.WebApp.initData` и вызывает серверную функцию `login_telegram(init_data)`.
3. Сервер проверяет подпись по алгоритму Telegram (HMAC-SHA256: ключ — HMAC от токена бота с `WebAppData`,
   сообщение — поля, кроме `hash`, по алфавиту через `\n`), проверяет `auth_date` (не старше 1 часа) и ищет
   клиента `telegram` по user id.
4. Ответ — короткий токен (15 минут) в теле, клиент хранит его в памяти и шлёт в `Authorization`.
   **Не cookie:** в Telegram Web Mini App работает во фрейме, и Safari блокирует там cookie.
5. Токен истёк — снова шаг 2 (`initData` ещё в странице).
6. Не привязан — экран «Подключите Telegram в настройках бюджета» со ссылкой на сайт.

Токен бота есть только на сервере, в клиенте — никогда.

**Экраны первой версии:** остатки по счетам, быстрая операция (как диалог быстрого расхода), «Входящие» с
подтверждением, бюджет за месяц.

**Возможности Telegram:** тема из `themeParams`, `MainButton` вместо кнопки на странице, `BackButton`,
вибрация при сохранении, сканер QR (`showScanQrPopup`) для тайских PromptPay-чеков, вход по отпечатку
(BiometricManager), ярлык на главный экран.

**Ограничения:** офлайна нет; размер WASM — цель ≤ 1 МБ по сети (brotli), первый экран — серверный рендер.

### 9.3. Оболочки клиентов

Telegram — не отдельная платформа для Dioxus, а наша оболочка поверх веб-сборки. Страницы в `client/ui` не
знают, где запущены: оболочка кладёт в контекст Dioxus свои реализации, страницы берут их через `use_context`.

| Контекст | web | telegram | mobile | desktop |
| --- | --- | --- | --- | --- |
| Вход | Rauthy, cookie | `initData` → токен в заголовке | токен устройства | токен устройства |
| Данные | серверные функции | серверные функции | SQLite + очередь | SQLite + очередь |
| Главная кнопка | на странице | `MainButton` | на странице | на странице |
| «Назад» | ссылка | `BackButton` | системный жест | ссылка |
| Тема | своя | `themeParams` | системная | системная |
| Язык | настройки | `language_code` | системный / настройки | системный / настройки |
| Сканер QR | — | `showScanQrPopup` | камера | — |
| Вибрация | — | `HapticFeedback` | системная | — |

Страница описывает действие («главная кнопка — „Сохранить“, по нажатию — `save()`»), оболочка решает, как его
показать. Отсюда правило: в страницах — слоты под главную кнопку и «Назад», а не сами кнопки.

**Две веб-сборки на одном сервере.** Сайт и Telegram — разные WASM-бандлы. Если два fullstack-приложения не
встают в один axum: (а) `telegram` — клиентская сборка, которая ходит в серверные функции из `client/api`;
(б) одна веб-сборка, которая во время работы видит `initData` и включает Telegram-оболочку. Выбор — на пилоте.

**Готово, когда:** бот привязывается и принимает пересылки, Mini App входит без пароля, четыре экрана работают
на трёх языках в светлой и тёмной теме Telegram, тесты проверки `initData`, гайд «Бюджет в Telegram» со
скриншотами, «Что нового», `Dockerfile` и CI собирают WASM.

## 10. Этап G. Синхронизация

### 10.1. Запись на устройстве

1. В одной транзакции SQLite: изменение (операция, справочник) + запись в `outbox`. Интерфейс показывает
   изменение сразу.
2. Сразу после записи — «толчок» фоновой задаче синхронизации, без ожидания.
3. Задача отправляет `outbox` пачкой по порядку (сначала новый счёт, потом операция по нему).
4. Сервер ответил по каждой записи: принято / уже было (тот же `client_id`) / конфликт / ошибка проверки.
   Принятое удаляется из `outbox`.
5. Нет сети или ошибка сервера — запись остаётся; повтор через 1 → 5 → 30 с → 1 → 5 мин (дальше каждые 5 мин),
   и сразу при появлении сети или открытии приложения.

Отдельного пути «есть сеть — сразу на сервер» нет: один путь проще и не теряет данные при обрыве посреди запроса.

### 10.2. Получение изменений

- На сервере — лента изменений проекта: таблица `fb_changes` (`project_id`, `seq` — монотонный номер, сущность,
  id, версия, время). Пишется в той же транзакции, что и изменение.
- Клиент запрашивает «всё после `seq` = N» пачками; хранит курсор в `sync_state`.
- После отправки `outbox` — сразу получение.
- Пока приложение открыто и есть сеть — WebSocket или SSE: сервер сообщает «есть новое», клиент забирает.
- Первый запуск — полный снимок проекта, дальше — лента.
- Удаления — «надгробия» в ленте. Нужно мягкое удаление `deleted_at` (дорожная карта, этап 1).

### 10.3. Версии и конфликты

- У каждой изменяемой записи — `version` (растёт при каждой правке на сервере).
- Новые операции не конфликтуют (двойная запись только добавляет проводки).
- Правка: устройство шлёт «правил версию 3». На сервере 4 — ответ «конфликт» с серверной версией; сервер ничего
  не перезаписывает молча.
- Приложение показывает обе версии и предлагает выбрать; выбранное уходит новой правкой.
- Справочники (счета, категории, места, люди) — так же; переименование одной записи с двух устройств — конфликт.
- Права проверяются на сервере при каждом приёме; отказ — запись помечается в приложении «не принято: нет прав».

### 10.4. Таблицы на устройстве

| Таблица | Что |
| --- | --- |
| зеркала: `transactions`, `entries`, `items`, `accounts`, `categories`, `places`, `people`, `currencies`, `rates`, `limits`, `plans` | копии серверных с `version` |
| `outbox` | `id`, сущность, действие, тело, `client_id`, `created_at`, попытки, последняя ошибка |
| `sync_state` | курсор `seq`, время последней синхронизации, версия протокола |
| `conflicts` | своя версия, серверная версия, когда |

Остатки на устройстве пересчитываются после каждой синхронизации; главные цифры — серверные.

### 10.5. Протокол (`sync-protocol`)

- `POST /api/sync/push` — пачка изменений из `outbox`, ответ по каждому.
- `GET /api/sync/pull?after=<seq>&limit=` — изменения и новый курсор.
- `GET /api/sync/snapshot` — полный снимок (первый запуск, сброс).
- `GET /api/sync/stream` — WebSocket/SSE «есть новое».
- Версия протокола в заголовке; сервер поддерживает текущую и предыдущую; старше — «обновите приложение».
- Вход — токен клиента `kind = device` (раздел 6).

### 10.6. Что видит пользователь

Значок: «✓ синхронизировано» / «⏳ ждёт отправки: N» / «⚠ нужно выбрать версию». Больше ничего.

**Готово, когда:** тесты протокола (обрыв посреди отправки, повтор, конфликт правки, удаление, первый снимок)
на PostgreSQL и SQLite; две копии приложения и сайт сходятся к одним цифрам.

## 11. Этап H. Android

Оболочка `client/mobile` + мостики на Kotlin.

### 11.1. Уведомления банка

- `NotificationListenerService` на Kotlin; доступ включает пользователь в настройках Android (приложение ведёт
  туда с объяснением).
- Слушаем только выбранные пользователем приложения банков; остальные уведомления не читаем и не сохраняем.
- Текст → Rust (`import`) → кандидат во «Входящих» на устройстве → подтверждение (или «сохранять сразу»).
- `external_ref` — из номера операции в тексте, иначе — хеш (приложение, время, текст).

### 11.2. Галерея

- Новые скриншоты: `ContentObserver` на MediaStore + WorkManager; только папка скриншотов (или выбранные
  папки).
- OCR на устройстве: Google ML Kit (тайский, русский, английский — проверить качество тайского на этапе H).
- Не похоже на чек или перевод — пропускаем, ничего не сохраняем.
- Также «Поделиться» → приложение (для любых картинок без доступа ко всей галерее).

### 11.3. Фон и система

- Синхронизация — WorkManager с условием «есть сеть».
- База зашифрована, ключ в Keystore; вход по отпечатку или лицу (по желанию).
- Push-уведомления (напоминания) — FCM или через бота Telegram; выбор — открытый вопрос.

### 11.4. Распространение

- Google Play: доступ к уведомлениям и `READ_MEDIA_IMAGES` проходят строгую проверку — нужны описание
  назначения, видео, страница о данных. Если не пропустят галерею — оставить «Поделиться» и выбор фото.
- RuStore и APK с сайта — для пользователей в России и как запасной путь.

**Готово, когда:** уведомление банка из списка (8.1) за ≤ 5 секунд становится кандидатом во «Входящих», работает
без сети, синхронизируется; страница о данных и гайд на трёх языках.

## 12. Этап I–J. Компьютер и iPhone

### 12.1. Компьютер и локальный MCP

- Оболочка `client/desktop`: та же SQLite и синхронизация.
- Команда `family-budget mcp` — MCP-сервер по stdio с теми же инструментами, что серверный (`crates/features/mcp`),
  но с локальным хранилищем. Claude Desktop запускает её сам.
- Права — тот же сервис прав (раздел 6), локальный клиент `kind = mcp` со своими правами; удаления нет.
- Записи Claude идут через `outbox`, как ручные; журнал — тоже.
- Данные из базы — только данные, не инструкции (как в серверном MCP).
- Риск: права проверяются на устройстве; подделать их может только владелец компьютера — и это его данные.
  Сервер всё равно проверит права при синхронизации.

### 12.2. iPhone

- Оболочка `client/mobile` для iOS + мостики на Swift.
- Уведомления — нельзя. Вместо них: «Поделиться» → приложение (скриншоты), «Быстрые команды» с автоматизацией
  «Транзакция» для Apple Pay (команда передаёт сумму и продавца в приложение).
- Галерея — PhotoKit, только пока приложение открыто, или выбор фото.
- OCR — Apple Vision.
- Фон — BGTaskScheduler, редкие окна; основное — синхронизация при открытии.

## 14. Безопасность и приватность

- Токен бота, ключи — только на сервере, в секретах.
- `initData` проверяется на сервере, свежесть — 1 час; токен Mini App — 15 минут, в заголовке.
- Привязка Telegram — одноразовый код, 10 минут.
- Токены устройств — отзываются на странице «Подключённые приложения»; отзыв — сразу.
- База на устройстве зашифрована; вход по биометрии по желанию.
- Уведомления — только выбранных банков; исходные тексты и скриншоты — минимальный срок хранения.
- Проект требует 2FA — клиенты, открытые без второго фактора, не работают (как MCP сейчас).
- Страница «Конфиденциальность» и «Удаление данных» на трёх языках — что читаем, что храним, где (Telegram,
  устройство, сервер), как удалить.
