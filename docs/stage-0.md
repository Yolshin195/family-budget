# Этап 0 — разбор ошибок расчётов (Ц) до правки

Разбор по каждому пункту Ц этапа 0 дорожной карты (`docs/roadmap.md`) в формате из спека новых фич: что
считается неверно, причина, исправление, что изменится в отчётах, миграция и откат, тест, сверка. **Код
расчётов не менялся** — правки начнутся после утверждения. Пункты безопасности (Б1–Б6) — не расчёты, они
делаются сразу и сюда не входят.

Данные — проект «Личный бюджет» (базовая валюта THB), снято через MCP 19.10.2026. Тесты, которые сейчас
падают, уже лежат в коде с пометкой `#[ignore = "Ц…: …"]`. Посмотреть, как они падают:
`cargo test --workspace -- --ignored`. Тест Ц10 работает только на PostgreSQL: нужен `TEST_DATABASE_URL`.
Исправление снимает `#[ignore]` со своего теста.

## Сверка «до» (одна на все пункты)

| Что | Значение 19.10.2026 |
| --- | --- |
| CARD_KBANK | 4 161,83 ฿ |
| CARD_TBANK | 15 470,55 ₽ |
| CASH_THB | −55,00 ฿ (нет начального остатка наличных — не ошибка расчёта) |
| Бюджет, сентябрь 2026 | расходы 0, доходы 0 (операции начинаются 15.10) |
| Бюджет, октябрь 2026 | расходы 7 787,93 ฿ (план 0), доходы 0 (план 56 915,20 ฿), «нет курса» — пусто |
| Бюджет, 2026 год | расходы 7 787,93 ฿ (план 9 500,00 ฿), доходы 0 (план 284 576,00 ฿) |
| Лимиты | нет ни одного правила |
| Планы | 5 (4 активных), оплачены 2 вхождения: «Электричество» 16.10 и перевод 16.10 |

**Итог сверки:** ни одна ошибка этапа 0 на текущих данных проекта не проявилась. Лимитов нет, у RUB есть
курс, тип категорий не менялся, обе оплаты планов указывают на настоящие даты правил, повторных начальных
остатков нет. Поэтому после всех исправлений остатки счетов и итоги бюджета за сентябрь–октябрь и за год
**не изменятся** — эту же таблицу снимаем ещё раз после выкладки. Примеры ниже показывают, что получилось бы
на этих же данных при одном действии пользователя.

## Решения, которые нужно утвердить

1. **Ц5.** Лимит, заведённый в середине месяца, действует на весь этот месяц, как и сейчас в месячном отчёте:
   «поставил лимит на октябрь 20-го». Альтернатива — пропорционально дням (1 500 × 12/31 = 580,65 ฿), но
   тогда лимит, заведённый в конце месяца, сразу «перерасходован».
2. **Ц5.** Правило с суммой 0 означает «с этой даты лимита нет». История прошлых периодов при этом остаётся.
3. **Ц3.** Сумма без курса не входит в итоги и показывается отдельно: «нет курса: 10 $». Поведение для дат
   *раньше первого курса* (сейчас берётся самый ранний курс) этап 0 не меняет — это решение группы 1.
4. **Ц4.** Прежний план закрывается, а новый создаётся только при смене *правила дат* (дата начала, повторение,
   интервал), и только если у плана есть вхождения в прошлом. Сумма, счёт, категория и название меняются на
   месте, как сейчас.
5. **Ц7.** Проверяем, что план есть в проекте, дата — дата его правила, а тип операции совпадает с типом
   плана. Сумма и счёт могут отличаться от плана (реальный случай: план 2 000 ฿, оплачено 1 539,87 ฿).
6. **Ц8.** Вместе с ограничением знаков запрещаем архивировать базовую валюту проекта (техдолг №40).

## Ц1 и Ц5. Лимит по периодам

**Что считается неправильно.** Лимитов в проекте нет, поэтому пример — что будет, если завести месячный лимит
1 500 ฿ на «Кофе и чай» (`FOOD_COFFEE`, 490 ฿ в октябре):

| Ситуация | Сейчас | Правильно |
| --- | --- | --- |
| Лимит с 01.01.2026, годовой отчёт | 17 661,29 ฿ (1 500 × 365/31) | 18 000 ฿ (12 × 1 500) |
| Лимит с 20.10.2026, годовой отчёт | 17 661,29 ฿ — как будто лимит был весь год | 4 500 ฿ (октябрь–декабрь) |
| Лимит с 01.01.2026, неделя 28.09–04.10 | 350,00 ฿ (1 500 × 7/30, вся неделя по сентябрю) | 343,55 ฿ (1 500 × 3/30 + 1 500 × 4/31) |
| Перестать ограничивать с 01.11 | нельзя: сумма должна быть > 0, остаётся только удалить правило, и тогда прошлые месяцы теряют лимит | «Снять лимит с даты» 01.11: до 31.10 лимит есть, дальше нет |
| Запретить себе категорию | нельзя: лимит 0 не принимается | лимит 0 — любая трата сразу перерасход |

**Причина.** `crates/features/budget/src/domain.rs:92-101` (`effective_limit`):

- на весь период отчёта берётся одно правило — последнее с `valid_from ≤ period.to`;
- длина «базы» берётся по первому подпериоду (`Period::containing(rule.period, period.from)` — январь, 31 день),
  и год делится на 31 день.

`crates/features/limits/src/domain.rs:81-86` (`positive`) не даёт сумму 0.

**Исправление.**

1. Каждое правило действует от начала своего подпериода, в который попал `valid_from`: месячное с 20.10 — с
   01.10, недельное со среды — с понедельника. Действует оно до начала подпериода следующего правила этой
   категории.
2. Лимит за отчёт = сумма по правилам: `сумма правила × Σ (дней подпериода внутри отчёта и внутри срока
   правила / дней подпериода)`.
3. Утверждено: 0 — настоящий нулевой лимит (любая трата — `over`, без трат — `ok`, процента нет). «Снять лимит
   с даты» — отдельное правило без суммы (`fb_limits.amount` NULL): вклада не даёт, но закрывает срок прежнего.
   Если в отчёт не попало ни одного действующего правила — лимита нет (`None`).
4. Округление — один раз, у итога (до 2 знаков, как сейчас; по точности валюты — это Ц9, этап 1).
5. В limits — сумма ≥ 0 и снятие: домен, форма (кнопка «Снять лимит с даты»), REST (`removed: true` без
   `amount`; в ответе `removed`, `effective_from`), MCP `set_limit` (`remove: true`) и `list_limits`.
6. В списке лимитов снятое правило помечено «лимит снят»; правило, которое начинает действовать раньше своей
   даты, показывает «действует с» начала периода.

**Что изменится.** Колонки «Лимит», «Доступно», уровень (ok / warn / over) в годовом и недельном бюджете,
в REST `/api/budget` и MCP `get_budget` для `week` и `year`. **Месячный отчёт не меняется:** для правила того
же месяца формула даёт то же число. Поэтому не меняются и остатки лимитов в быстром расходе и в `get_context` —
они месячные. Новое значение правильное: в году 12 месяцев, а лимит действует только с месяца, когда его завели.

**Миграция.** `limits/migrations/20261019053911_removed_limit`: `amount` допускает NULL («лимит снят»),
`CHECK (amount IS NULL OR amount >= 0)`. Данные не меняются. Откат (down): правила «лимит снят» удаляются,
`amount` снова `NOT NULL`.

**Тесты.**

- `budget::domain::tests::monthly_limit_in_year_report_is_twelve_months` — было 17 661,29 вместо 18 000;
- `budget::domain::tests::limit_counts_from_its_month_only` — было 17 661,29 вместо 4 500;
- `budget::domain::tests::week_across_months_takes_both_months` — 343,55;
- `budget::domain::tests::rule_change_inside_year` — 39 000 за год, недельное правило со среды — с понедельника;
- `budget::domain::tests::zero_limit_means_no_spending`, `removed_limit_keeps_the_past`;
- `limits::domain::tests::zero_limit_and_removed_limit`, `limits::tests::removed_limit_has_no_amount`,
  `mcp::tests::zero_limit_and_removed_limit`.

**Сверка после:** лимитов нет — цифры из таблицы «до» не меняются.

## Ц2. Тип категории меняется при существующих операциях

**Что считается неправильно.** Пример — `PINPAN`: расходная корневая категория без подкатегорий, 950,75 ฿ в
октябре. Если в форме сменить ей тип на «доход», изменение сохранится. В октябрьском бюджете тогда:

- шапка «Расходы» по-прежнему 7 787,93 ฿ — она считается по типу операций;
- сумма строк дерева расходов — 6 837,18 ฿;
- в дереве доходов появится `PINPAN` 950,75 ฿ при «Доходы 0».

Итоги и деревья перестают сходиться. Новые расходы на `PINPAN` после этого не создать, а старые редактируются
(техдолг №3).

**Причина.** `crates/features/categories/src/domain.rs:131` (`change`) переписывает `category_kind` без условий.
У фичи categories нет портов (`ports.rs`, пустой `Deps`), поэтому она не знает, есть ли у категории операции,
планы или лимиты.

**Исправление.**

1. Порт `CategoryUsage` в categories: «используется ли код» (проводки на категорию, планы, лимиты). Адаптер —
   в `crates/app/src/wiring/wire_categories.rs` через публичные методы transactions, planning, limits. Так же
   уже сделана проверка «валюта счёта при проводках» в accounts.
2. `update` при смене типа используемой категории возвращает ошибку валидации: «по категории есть операции,
   планы или лимиты — тип не меняется».
3. Подкатегории проверять отдельно не нужно: `check_tree` и так требует, чтобы у потомков был тот же тип.
   Значит, сначала пришлось бы менять их, и каждая проверилась бы.
4. Через MCP `update_category` идёт тот же сервис.

**Что изменится.** Числа — нет. Запрещается действие, которое их портило.

**Миграция.** Не нужна. Испорченных данных нет: среди 38 операций с 01.09 по 19.10 — расходы на расходные
категории, два перевода и два начальных остатка, доходов нет. Перед выкладкой владелец может проверить запросом «проводки на категории,
тип которых не совпадает с типом операции» — его приложу к PR.

**Тест.** `categories::tests::kind_change_with_postings_is_rejected` — сейчас тип меняется. С исправлением тест
получит фейк порта: «используется» → ошибка, «не используется» → тип меняется.

**Сверка после:** без изменений.

## Ц3. Без курса валюты складываются 1:1

**Что считается неправильно.** У RUB есть курсы с 16.10, поэтому на данных проекта `missing_rates` пусто и
ошибки нет. Пример: заведите счёт в USD без курса и потратьте 10 $ в кафе. Октябрьские расходы станут
7 797,93 ฿ — 10 $ посчитаны как 10 ฿. Правильный итог без курса не известен, поэтому нельзя показывать число,
будто оно верное. В тестовом проекте: 300 ฿ + 10 $ без курса → «Расходы 310» вместо 300 и «нет курса: 10 $».
Быстрый расход так же молча считает остаток лимита по курсу 1.

**Причина.**

- `crates/features/budget/src/service.rs:90-101` (`convert`): без курса возвращает сумму как есть и только
  запоминает валюту в `missing_rates`.
- `crates/features/transactions/src/service.rs:228` (`quick_defaults`): `unwrap_or(Decimal::ONE)`.
- В `crates/features/planning/src/domain.rs:273` уже правильно: `None`.

**Исправление.**

1. Одна функция «курс на дату» в kernel. Это первый шаг техдолга №22: правило то же — последний курс не позже
   даты, раньше первого курса — самый ранний. Её используют budget, planning и transactions.
2. В budget сумма без курса не входит ни в факт, ни в план, ни в итоги, ни в курсовую разницу. Она собирается
   в строку категории как «нет курса: 10 $», а предупреждение над отчётом пишет «не вошло в итоги» — на трёх
   языках.
3. Прогноз остатков: плановый перевод в валюту без курса не пересчитывается в счёт зачисления и помечается
   «нет курса».
4. Быстрый расход: `rate_to_base` у счёта без курса пустой, а форма пишет «нет курса» вместо остатка лимита.
5. MCP `get_budget` отдаёт по категории `unconverted` (валюта, сумма).

**Что изменится.** Итоги бюджета, факт и прогноз категорий — только у проектов, где есть валюта без курса. Их
итоги станут меньше на неконвертированные суммы, а эти суммы будут видны отдельно. Новое значение правильное:
итог состоит только из сумм в базовой валюте, неизвестное не выдаётся за известное.

**Миграция.** Не нужна. Откат — откат кода.

**Тест.** `budget::tests::amount_without_rate_is_not_summed` — сейчас расходы 310 вместо 300.

**Сверка после:** у всех валют проекта есть курс — цифры не меняются.

## Ц4. Правка правила плана задним числом теряет оплаты

**Что считается неправильно.** План «Электричество»: ежемесячно с 16.10, 2 000 ฿. Вхождение 16.10 оплачено
17.10 суммой 1 539,87 ฿. Если сменить дату начала на 01.10 (счёт теперь приходит 1-го):

- календарь за октябрь покажет только «01.10 — просрочено 2 000 ฿», а оплата 16.10 из плана пропадёт (операция
  останется, но ни к чему не привязана);
- просроченное вхождение входит в план бюджета, поэтому прогноз расходов октября станет 9 787,93 ฿ вместо
  7 787,93 ฿;
- в нём будет и факт 1 539,87 ฿, и план 2 000 ฿ за один счёт.

**Причина.** `crates/features/planning/src/service.rs:55-62` (`update`) переписывает правило на месте.
Вхождения строятся только по текущему правилу (`planning/src/domain.rs:171-213`), а оплаты и пропуски
привязаны к паре «план + дата». Старые даты перестают существовать, новые прошлые даты становятся
«просроченными».

**Исправление.**

1. Если меняется правило дат (дата начала, повторение, интервал) и у плана есть вхождения раньше «сегодня»:
   - прежний план закрывается: `end_on` — вчера или дата последнего решённого вхождения, если оплатили
     заранее;
   - создаётся новый план с новыми полями; он начинается с первой даты нового правила не раньше сегодняшней;
   - ответ сервиса и формы — новый план с сообщением «Правило изменено с <дата>, прошлые оплаты остались в
     прежнем плане» на трёх языках.
2. Иначе, как сейчас, правка на месте.
3. «Сегодня» — как везде до Ц6 (этап 1, по спеку — PR 1 группы 1).
4. MCP `update_plan` идёт через тот же сервис.

**Что изменится.** Календарь, «Предстоящие» и план и прогноз бюджета — только у планов, которым меняют дату
задним числом. Новое значение правильное: оплаченное остаётся оплаченным, прошлые даты нового правила не
становятся долгом.

**Миграция.** Не нужна. Повреждённых данных нет: оба оплаченных вхождения («Электричество» 16.10 и разовый
перевод 16.10) совпадают с датами своих правил. Запрос для проверки «оплаты, чьи даты не входят в правило»
приложу к PR.

**Тест.** `planning::tests::rule_change_keeps_payment_history` — сейчас за октябрь
`[(01.10, OVERDUE)]` вместо `[(16.10, PAID)]`.

**Сверка после:** без изменений.

## Ц7. План и дата оплаты не проверяются

**Что считается неправильно.** Обе оплаты в проекте корректны. Ошибка проявится, если через REST
(`POST /api/transactions`) или подправленную форму передать `plan_date` = день платежа, а не дату плана.
Например, «Электричество» с `plan_date` 17.10:

- операция сохранится;
- 16.10 останется просроченным, и прогноз октября станет 9 787,93 ฿ вместо 7 787,93 ฿, как в Ц4;
- оплата 17.10 в календаре не видна — такой даты в правиле нет.

Так же принимается `plan_id` несуществующего плана или плана другого проекта. MCP `pay_planned` это проверяет,
а остальные входы — нет.

**Причина.** `crates/features/transactions/src/service.rs:49-57` (`create`) и `:81-91` (`update`) проверяют
только, что `plan_id` и `plan_date` заданы вместе (`dto.rs:204`). Порта к planning у transactions нет.

**Исправление.**

1. Порт `PlanLookup` в transactions: «вхождение плана на дату» → тип плана или «нет». Адаптер — в
   `wire_transactions.rs` через `planning::occurs_on`.
2. При создании и при смене плана в операции проверяется, что план есть в проекте, дата — дата правила, а тип
   операции равен типу плана. Иначе ошибка `plan_date`.
3. Если план у операции не менялся, при правке проверка пропускается, как для «старых» ссылок.
4. Существующий тест `plan_occurrence_is_paid_once_and_freed_on_delete` получит фейк порта.

**Что изменится.** Числа — нет. Запрещается запись, которая их портила.

**Миграция.** Не нужна. Запрос для поиска неверных ссылок приложу к PR. На данных проекта таких ссылок нет.

**Тест.** `transactions::tests::unknown_plan_occurrence_is_rejected` — сейчас оплата несуществующего плана
принимается.

**Сверка после:** без изменений.

## Ц8. Точность валюты и архив валюты

**Что считается неправильно.** У THB и RUB по 2 знака. Если в форме валюты поставить THB 0 знаков, это
сохранится. Тогда операции 1 539,87 ฿ («Электричество») и 151,75 ฿ (Rosmuemae) больше не исправить: «у THB не
больше 0 знаков». Число 7 принимается, хотя суммы в БД хранятся с 4 знаками; −1 принимается и молча работает
как 0 (`wire_transactions.rs:30`). Архивация RUB при активном счёте `CARD_TBANK` тоже сохранится. После неё
счёт нельзя изменить («currency_code: запись 'RUB' не найдена», `accounts/src/service.rs:165`), а базовую
валюту THB можно архивировать.

**Причина.** `crates/features/currencies/src/domain.rs:90` (`create`) и `:102` (`change`) не проверяют
`minor_units`. `crates/features/currencies/src/service.rs:60` (`archive`) архивирует без проверок.

**Исправление.**

1. Домен: `0 ≤ minor_units ≤ 4`.
2. Уменьшать число знаков можно, только если в этой валюте нет проводок (порт `CurrencyUsage` → transactions:
   `fb_postings.currency_code`). Увеличивать можно всегда.
3. Архив запрещён, если в валюте есть активные счета (порт → accounts) или это базовая валюта проекта.
4. Миграция currencies: `CHECK (minor_units BETWEEN 0 AND 4)`.

**Что изменится.** Числа — нет. Запрещаются действия, после которых данные противоречат настройке.

**Миграция.** Перед `CHECK` миграция проверяет, нет ли значений вне 0–4. Если есть — останавливается с
перечнем валют (без тихой правки). У проекта RUB и THB по 2 знака. Откат:
`ALTER TABLE fb_currencies DROP CONSTRAINT …`.

**Тест.** `currencies::tests::minor_units_are_bounded` — сейчас 7 и −1 принимаются. С исправлением добавятся
«уменьшение при проводках» и «архив при активном счёте или базовой».

**Сверка после:** без изменений.

## Ц10. Начальный остаток можно записать дважды

**Что считается неправильно.** Начальные остатки есть у `CARD_TBANK` (41 768,66 ₽) и `CARD_KBANK`
(1 961,31 ฿), по одному. Если у `CASH_THB` задать остаток 500 ฿ и дважды быстро нажать «Сохранить», могут
записаться два начальных остатка. Тогда `CASH_THB` будет 945 ฿ вместо 445 ฿. Проверено на PostgreSQL 16: два
одновременных `set_opening` записали два остатка (не каждый раз — это гонка). Второй остаток, записанный
напрямую, база принимает всегда.

**Причина.** `crates/features/transactions/src/service.rs:143-165` (`set_opening`) и `:318-328`
(`check_opening`): сначала чтение «остатка ещё нет», потом вставка. Ограничения в БД нет, а у шапки операции
нет колонки счёта: счёт есть только в проводках.

**Исправление.**

1. Миграция transactions добавляет к `fb_transactions` колонку `opening_account TEXT NULL`. Она заполняется
   только у OPENING, и это закрепляет `CHECK ((tx_kind = 'OPENING') = (opening_account IS NOT NULL))`.
2. Уникальный индекс `(project_id, opening_account) WHERE tx_kind = 'OPENING'`.
3. Нарушение индекса → `Conflict`. `set_opening` на `Conflict` перечитывает остаток и обновляет его, поэтому
   повторное нажатие безопасно.

**Миграция.**

- Заполняет колонку из проводок OPENING.
- Если у какого-то счёта уже два OPENING, миграция останавливается с перечнем (без тихого удаления). У проекта
  повторов нет.
- Откат: `DROP INDEX`, `DROP COLUMN` (поле служебное, данных не теряем).

**Тест.** `transactions::tests::second_opening_is_rejected_by_db` — сейчас второй остаток принимается. В CI
Postgres нет (техдолг №10), там тест пропускается. Локально:

```bash
TEST_DATABASE_URL=postgres://… cargo test -p transactions -- --ignored second_opening
```

**Сверка после:** без изменений — повторов нет.
