# Промт для запуска сервиса входа (отдельный репозиторий)

Скопируйте всё ниже линии в первую сессию Claude Code в новом репозитории. Перед этим замените
`<сервис>` (имя сервиса и репозитория, например `id`) и `<домен>` (свой домен; сервис будет на `id.<домен>`).

---

Ты начинаешь разработку **<сервис>** — собственного сервиса регистрации и входа (OpenID Connect провайдер +
сервер авторизации OAuth 2.1) для моих проектов с **бесшовным входом** между ними. Первый клиент — «Семейная
бухгалтерия» (репозиторий `Yolshin195/family-budget`, Rust/Axum; подключи его для чтения через `add_repo`, когда
нужно свериться с кодом). Сервис заменит Rauthy, который сейчас стоит у бухгалтерии.

Сначала прочитай задачу целиком, задай мне вопросы по разделу «Открытые решения» и по всему, что неясно, затем
напиши ТЗ и план (раздел «Как работать»). Код — только после моего «да» на ТЗ.

## 1. Зачем и для кого

- Семья (Таиланд + русскоязычные) и, возможно, внешние пользователи моих сайтов; открытая регистрация.
- Главное — **удобство регистрации и входа для пользователей**: один тап, без паролей, страницы в стиле моих
  приложений, на трёх языках.
- Один вход на все мои проекты: вошёл в одном — в остальных уже вошёл; «выйти везде» — из всех.
- Доступ AI-ассистентов к моим приложениям через MCP: сервис выдаёт им токены (сначала только для Claude).

Почему не готовое решение (проверено в октябре 2026): Rauthy — нет тайского, нет TOTP, выход без
`id_token_hint` не возвращает на сайт, с Claude не стыкуется CIMD; Zitadel, Ory, Pocket ID, Casdoor, Kanidm,
Hanko — нет тайского и/или Telegram, и/или CIMD + RFC 8707 для MCP, и/или лишние сервисы и память.

## 2. Способы входа

**Почта не обязательна.** Аккаунт — это набор способов входа; достаточно любого одного, рекомендуем два.

| Способ | Версия | Детали |
| --- | --- | --- |
| **Passkey** | v1, основной | `webauthn-rs` (Passkey API, без аттестации): Touch ID / Face ID, синхронизация iCloud Keychain и Google Password Manager; автоподстановка в поле входа (conditional UI); discoverable credentials — вход без ввода логина; несколько passkey на аккаунт с названиями устройств |
| **Telegram** | v1 | Стандартный OpenID Connect `https://oauth.telegram.org` (discovery `/.well-known/openid-configuration`, code + PKCE S256), ключи — @BotFather → Bot Settings → Web Login. **Email не отдаёт**, `sub` — числовой id. В начале работы проверь актуальную документацию (core.telegram.org/bots/telegram-login) и claims; старый Login Widget с HMAC не использовать |
| Код на email | v1.1, необязательный | Для тех, у кого нет Telegram, и как ещё один способ восстановления: 6 цифр, 10 минут, 5 попыток, лимиты по адресу и IP, в БД — хеш. Нужен SMTP — до этой версии сервис работает без почты |
| Google, LINE, Apple | позже | Через общий адаптер OIDC (`openidconnect`) |
| GitHub, Facebook | позже | Через общий адаптер OAuth2 (`oauth2`) |

- Новые способы — адаптеры одного порта (`UpstreamProvider` для внешних, свой модуль для passkey/кодов);
  добавление способа не трогает остальной код.
- Регистрация: «Войти через Telegram» (один тап) **или** «Создать passkey» (имя → Touch ID). Сразу после
  регистрации — мягкое предложение добавить второй способ (passkey на этом устройстве / Telegram).
- Паролей нет вообще — ни при регистрации, ни для восстановления.
- Привязка нового способа — только к уже вошедшему пользователю (никакого автосклеивания аккаунтов по совпадению
  email или имени).
- Восстановление: войти любым другим привязанным способом. Если способов не осталось — **одноразовая ссылка
  восстановления от администратора** (команда CLI `<сервис> recovery-link <аккаунт>`, ссылка на 24 часа, событие в
  журнал). Для семейного масштаба это нормальный последний рубеж.
- `amr` в ID-токене — по RFC 8176, маппинг задокументировать. Passkey с проверкой пользователя (UV) должен давать
  признак сильного входа (`mfa` вместе с `hwk`/`swk`), Telegram и код на email — нет. Бухгалтерия считает вторым
  фактором любое из: `mfa`, `otp`, `hwk`, `swk`, `sms`, `fpt`, `face`, `iris`, `pop` (её «Требовать 2FA» на деле станет
  «требовать passkey»).

## 3. Протоколы

**OpenID Connect провайдер** (для моих приложений):
- Discovery, JWKS; подпись EdDSA (Ed25519), ротация ключей с перекрытием; authorization code + **PKCE S256
  обязательно**, `state`, `nonce`, `prompt=none` (тихий вход для SSO), `max_age`, `auth_time`, `sid`.
- ID-токен: `sub` (стабильный, не зависит от способа входа), `name`, `preferred_username`, `picture`, `locale`,
  `email`/`email_verified` — **только если email привязан и подтверждён**, `amr`. Userinfo.
- Refresh-токены с ротацией и обнаружением повтора (окно терпимости несколько секунд для одновременных запросов).
- **RP-Initiated Logout**: зарегистрированный `post_logout_redirect_uri` — возврат без экрана подтверждения
  (подтверждение — только при неизвестном клиенте).
- **Back-Channel Logout** (OIDC): при выходе, «выйти везде», отзыве сессии, удалении аккаунта — logout token всем
  приложениям, где была сессия. Плюс событие «аккаунт удалён» приложениям (back-channel, подписанное).
- Ответ авторизации с `iss` (RFC 9207). Отзыв токенов — RFC 7009, интроспекция — RFC 7662 (для серверов ресурсов).

**Сервер авторизации OAuth 2.1 для MCP** (v1.2, но модель данных закладывается сразу):
- Метаданные RFC 8414 с `client_id_metadata_document_supported: true`, `token_endpoint_auth_methods_supported`
  содержит `"none"`, `code_challenge_methods_supported: ["S256"]`, `authorization_response_iss_parameter_supported`.
  `offline_access` не объявлять.
- Клиенты: **CIMD** (Client ID Metadata Document) — скачивать только с хостов из белого списка (сначала Claude),
  без перенаправлений, ≤ 16 КБ, таймаут 5 с, кэш ≤ 24 ч, `redirect_uri` — точное совпадение и в белом списке
  (`https://claude.ai/api/mcp/auth_callback`, loopback `http://localhost|127.0.0.1:<порт>/callback` для Claude Code);
  плюс заранее заведённые публичные клиенты. Открытую DCR (RFC 7591) **не делать** (в MCP 2026-07-28 устарела).
- **RFC 8707**: `resource` → `aud` токена; ресурсы (MCP-серверы приложений) заранее зарегистрированы в конфиге.
  Токен одного ресурса не принимается другим.
- **Делегированное согласие**: после входа сервис отправляет пользователя на страницу согласия **приложения-ресурса**
  (например, бухгалтерия: выбор проекта и прав), передавая короткоживущий `consent_challenge`; приложение через
  серверный API сервиса (с секретом клиента) читает запрос и принимает/отклоняет его, передавая итоговые `scope` и
  свои claims (например, `project_id`); сервис выпускает токен. Образец — consent flow Ory Hydra.
- Access-токен — 1 час; refresh — ротация, 60 дней с последнего использования; повтор refresh → отзыв гранта;
  `scope` шире выданного при обновлении → `invalid_scope`.
- Строго по OAuth 2.1 и **RFC 9700** (Security BCP). Без implicit, password grant, секретов у публичных клиентов.

Требования Claude к коннекторам (проверь актуальность на claude.com/docs/connectors): `401` без токена,
Claude берёт только первый `authorization_servers`, `resource` в метаданных ресурса = введённый URL дословно,
токен-эндпоинт принимает form-urlencoded и отвечает ≤ 10 с, мёртвый refresh → `invalid_grant`, сервер доступен по IPv4.

## 4. Аккаунт и страницы

- Вход, регистрация, согласие (свой для OIDC-клиентов, делегированный для MCP), выход.
- Личный кабинет: имя, аватар, язык, тема; **способы входа** (добавить/удалить passkey, привязать/отвязать
  Telegram; нельзя удалить последний способ); **устройства и сессии** (выйти на одном / везде — с back-channel
  logout во все приложения); **подключённые приложения и ассистенты** (отозвать); журнал безопасности (год);
  удаление аккаунта.
- Языки ru / en / th — все страницы, сообщения об ошибках, письма (когда появятся), даты и числа в формате языка;
  язык: параметр `ui_locales` от приложения → cookie → Accept-Language → ru. Тайские тексты — пометить для
  проверки носителем.
- Дизайн — как у бухгалтерии (`Yolshin195/family-budget`: `tailwind.config.cjs`, `styles/app.css`): Inter + Noto Sans
  Thai, один акцент (индиго), светлая/тёмная тема по системе, мобильная вёрстка первой, цели ≥ 44 px, WCAG 2.1 AA.
  Логотип и название приложения-клиента на странице входа («Вход в Семейную бухгалтерию»).
- Без JS-фреймворков: Askama + минимальный свой JS (WebAuthn, conditional UI); htmx — по необходимости.

## 5. Нефункциональные требования

- Rust 2024, Axum 0.8, Askama, sqlx 0.8 + PostgreSQL (своя база в моём существующем PostgreSQL 16), tokio.
  Архитектура — эталон скилла `rust-hex-api` (Cargo workspace, фича = крейт, порты и адаптеры, связки в
  `app/wiring`); отклонения обоснуй в ТЗ. Если эталон чего-то не покрывает (OIDC, свой UI) — расширяй в проекте.
- Один бинарь/контейнер, цель — **< 64 МБ RAM** в покое; многоархитектурный образ (amd64/arm64) в GHCR.
- Клиенты, ресурсы MCP, белые списки — в файле конфигурации (TOML) + переменные окружения; секреты — из
  окружения или `*_FILE`. Продакшен не стартует без HTTPS, секретов и ключей.
- Безопасность (цель — OWASP ASVS уровень 2): cookie `__Host-` (HttpOnly, Secure, SameSite=Lax), id сессий и
  токены в БД — только хеши; CSRF (HMAC-токен + Origin); CSP без `unsafe-inline`/`unsafe-eval`, HSTS,
  `frame-ancestors 'none'`; лимиты запросов (по IP, аккаунту, клиенту); тело ≤ 64 КБ; таймауты; журнал
  безопасности; проверка `Host`.
- Тесты: юнит-тесты без БД (memory-репозитории), интеграционные с PostgreSQL; **OpenID Conformance Suite**
  (официальный, в Docker) — профили Basic OP, Config OP, RP-Initiated Logout, Back-Channel Logout — в CI;
  отдельный тест на каждую атаку из RFC 9700; `cargo audit`, `cargo deny`, Trivy, ZAP baseline; Renovate.
- Эксплуатация: `compose.yaml` для локальной разработки (сервис + PostgreSQL + бухгалтерия как тестовый клиент),
  развёртывание на том же VDS за Caddy (`id.<домен>`), резервные копии базы (age, три копии: свежая, 1–6 и 7–12
  дней), проверка восстановления, health-check. Документация на русском: README, `docs/deploy.md`,
  `docs/integrate.md` (как подключить новый проект за 10 минут).

## 6. Интеграция с бухгалтерией и переезд с Rauthy

- Бухгалтерия уже клиент OIDC: порт `IdentityProvider` + адаптер на `openidconnect`
  (`crates/features/projects/src/adapters/oidc.rs`), PKCE, `nonce`, проверка ID-токена по JWKS, `amr` для 2FA,
  свои сессии, удаление пользователя у провайдера при удалении аккаунта. Сервис должен работать с ней **без
  изменений протокола** — меняется только адрес провайдера (кроме пунктов ниже).
- В этом репозитории: тестовый клиент бухгалтерии в `compose.yaml`, сквозной тест «вход → бухгалтерия → второй
  клиент без повторного входа → выйти везде → обе сессии закрыты».
- Что потом поменять **в бухгалтерии** (не в этом репозитории, но опиши в `docs/integrate.md`): email
  необязателен (`fb_users.email` сейчас `NOT NULL`, приглашения в проект — по email → добавить приглашение
  ссылкой); удаление аккаунта — по событию back-channel вместо Admin API Rauthy; приём back-channel logout;
  MCP-согласие (выбор проекта и прав) — страница делегированного согласия.
- Переезд пользователей: на время перехода бухгалтерия принимает оба провайдера; вошедший через Rauthy
  пользователь нажимает «Перейти на новый вход» → входит в <сервис> → бухгалтерия связывает новый `sub` со
  своим пользователем. Потом Rauthy выключается.

## 8. Открытые решения (спроси меня в начале)

1. Домен сервиса и `rpId` для passkey: `id.<домен>` или `<домен>` (passkey привязан к домену — смена домена
   потребует создать их заново; техническим доменом хостера не пользоваться).
2. Разрешать ли регистрацию только по passkey (без Telegram) — удобно для тех, у кого нет Telegram, но
   восстановление тогда только через синхронизацию passkey или администратора.
3. Email: делать в v1.1 или позже; какой SMTP.
4. Лицензия и публичность репозитория.

## 9. Как работать

- Сначала: вопросы → `docs/spec.md` (ТЗ по разделам выше, модель данных, эндпоинты, экраны, угрозы и меры) →
  план по этапам → ждать моего одобрения.
- Дальше — этап за этапом, маленькими коммитами, с тестами; не сообщать «готово» без зелёных `cargo test`,
  `cargo clippy`, `cargo deny`. Не отходить от требований без согласования; спорное — в ADR и вопрос мне.
- Всё, что зависит от внешних сервисов (Telegram OIDC, требования Claude, версии крейтов), — сверять с актуальной
  документацией в начале этапа, а не по памяти.
